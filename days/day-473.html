المشكلتين

المشكلة ١: batch واحد سيء. التدريب شغال نضيف من إمبارح، وفجأة الـ loss curve بتروح عمودي عند step 8,217. السبب batch واحد الـ gradient norm بتاعه 4,200، يعني عشرين ضعف أعلى peak قبله. من غير clipping الـ optimizer بينفّذ step يمسح كل اللي الموديل اتعلمه في الساعة اللي فاتت. ومع global L2 clip على norm = 1.0، نفس الـ batch بيساهم بـ update طوله 1، والـ loss بيفضل على خطه، والـ run بيعيش.

المشكلة ٢: الـ FP16 مداه ضيق. الـ mixed precision بيزوّد الـ throughput 2–3× لأنه بيحسب الـ forward ومعظم الـ backward بـ FP16. التمن: الـ exponent range ضيق. gradient عادي ممكن يعمل overflow في FP16 فيبقى Inf، والـ Inf بيتحوّل لـ NaN في الطبقات اللي بعده، والـ NaN بيخلّي كل الـ weights NaN في الـ optimizer step الجاي.

تشبيه: clipping زي مُحدّد السرعة في العربية: مهما دُست بنزين، ما تعديش حد معيّن. والـ GradScaler زي مكبّر صوت قدام ميكروفون ضعيف: بتكبّر الإشارة الصغيرة (الـ gradients الصغيرة اللي كانت هتضيع في FP16) وبعدين بتصغّرها تاني. ولو الصوت اتشوّه (Inf)، بتشيل الـ step ده وتخفّض الـ volume.

معمل ١: الـ clipping على spike

٨ steps، واحد فيهم spike. حرّك حجم الـ spike والـ max_norm وشوف الـ norm قبل وبعد الـ clip.

لاحظ: الـ steps العادية (norm أقل من الحد) بتفضل زي ما هي. الـ spike بس هو اللي بيتقصّ لـ max_norm. الصيغة: scale = max_norm / (pre_clip + 1e-12) وبتتضرب في كل الـ gradients، فالاتجاه ما بيتغيّرش وطوله بس هو اللي بيتحدد.
02

الـ Global L2 norm والـ clipping

الـ global L2 norm هو الطول الإقليدي للـ gradient vector كله مدموج، مش norm لكل parameter لوحده. في PyTorch ده torch.nn.utils.clip_grad_norm_(parameters, max_norm)، والدالة بترجّع الـ norm قبل الـ clip، وده ضروري عشان نسجّل القيمة الطبيعية والقيمة بعد القص، ونشخّص حالة «إحنا بنقصّ في كل step».

pre_clip = sqrt( Σ over all params Σ grad² ) if pre_clip <= max_norm: no change (post_clip = pre_clip) else: grads *= max_norm / pre_clip (post_clip = max_norm)
تشبيه: تخيّل سهم (gradient) طوله 4,200. clipping بيقصّره لطول 1 من غير ما يغيّر اتجاهه. الموديل لسه ماشي في الاتجاه الصح بس بخطوة محسوبة.

وmax_norm = 1.0 هو الـ default الحديث لتدريب اللغة. الحد ده بيتحط في نفس الـ config بتاع الـ schedule (درس 44). الحدود الأكبر بتخلّي الموديل يتعافى من batches صعبة فعلًا، والأصغر بتحدد أسوأ حالة على حساب loss curve أكتر ضوضاء.

03

autocast وGradScaler

torch.amp.autocast(device_type) هو الـ context manager اللي بيشغّل العمليات المؤهلة (معظم الـ matmul-class) بـ FP16. وtorch.amp.GradScaler(device_type) بيضرب الـ loss في معامل كبير قبل الـ backward ويقسم الـ gradients على نفس المعامل قبل الـ optimizer step. الاتنين مصمّمين مع بعض: استخدام واحد من غير التاني بيبقى configuration error.

إزاي الـ scaler بيضبط المعامل

  • لو لقى Inf أو NaN في الـ gradients بعد الـ unscale: بيتخطى الـ step ويخفّض المعامل للنص.
  • لو آخر N steps كانوا سليمين: بيضاعف المعامل.
  • على مدى التدريب المعامل بيلاقي أعلى قيمة يسمح بيها مدى FP16.
تشبيه: أنت بتبعت طرد بالبريد وبتزوّد الغلاف الواقي (scale) طالما الطرد بيوصل سليم. أول ما طرد يوصل مكسور (Inf) بتقلّل الغلاف للنص وتجرّب تاني، وبعد كام طرد سليم بتزوّد تاني. بتدوّر على أكتر غلاف مفيد من غير ما تضيّع شحن.
على الـ CPU: الدرس بيستخدم CPU autocast لأنه اللي بيشتغل في CI. الـ GradScaler على CPU مجرد stub (الـ CPU autocast أصلًا بيستخدم BF16 ومش محتاج loss scaling)، بس الـ call sites موجودة عشان الـ wiring يطابق GPU loop بالظبط. في الكود فعلًا: GradScaler(device_type, enabled=(device_type == "cuda")) والـ amp_dtype الافتراضي هو bfloat16 على CPU وfloat16 غيره. الانتقال للـ GPU = غيّر device_type="cpu" لـ "cuda".

معمل ٢: ليه محتاجين loss scaling أصلًا؟

اختار حجم gradient صغير وعامل scale. الـ FP16 بيقدر يمثّل أرقام تقريبًا بين 6e-8 و65504 (أرقام عامة عن FP16، مش من الدرس). تحت الحد الأدنى بتبقى 0 (underflow)، وفوق الأقصى بتبقى Inf (overflow).

لاحظ: gradient صغير جدًا من غير scale بيضيع (يتحوّل لصفر). ومعاه scale مناسب بيدخل المدى. ولو الـ scale كبير زيادة، يعدّي 65504 ويبقى Inf. وده بالظبط اللي الـ scaler بيتجاوب معاه بـ skip وخفض المعامل.
04

الترتيب الصح: أهم سطر النهاردة

لو clip قبل unscale، الـ threshold بيتطبّق على gradients مضروبة في الـ scale. الترتيب الصح الوحيد:

1. scaler.scale(loss).backward() 2. scaler.unscale_(optimizer) 3. clip_grad_norm_(...) 4. scaler.step(optimizer) 5. scaler.update()

أي ترتيب تاني بيطلّع loop بايظ بصمت. والـ update() بيتنادى في كل step حتى لو skip: على step سليم بيزوّد الـ counter وممكن يضاعف المعامل، وعلى step متخطّى بيخفّضه للنص ويصفّر الـ counter. نسيان الـ update() على مسار الـ skip هو البج اللي بيطلّع «الـ scaling factor ما اتغيّرش أبدًا».

اكتشاف NaN وInf في مكانين

  1. الـ loss نفسه قبل الـ backward بـ torch.isfinite. الـ loss غير المنتهي ما بيطلّعش gradients مفيدة، فبنتخطاه من غير ما ندخل الـ optimizer.
  2. الـ gradients بعد scaler.unscale_(optimizer) بـ has_non_finite_grad(...).

الاتنين مع بعض بيغطّوا فشل الـ forward وفشل الـ backward.

تفصيلة دقيقة في الكود: مسار «الـ loss غير منتهي» بيتخطى من غير ما ينادي scaler.update()، لأننا ما نادّيناش scaler.scale(loss).backward() في الـ step ده، ونداء update() هنا هيكسر ترتيب الـ API المطلوب من GradScaler. أما مسار «الـ gradient غير منتهي» فبينادي update(). ده مش تناقض مع «update كل step»: القاعدة تنطبق على الـ steps اللي عدّت من scale().backward().

معمل ٣: الـ step الكامل بالترتيب (مع مسار الـ skip)

دوس «التالي». بنمشي في AmpTrainState.step من الـ forward لحد الـ log.

النمطالفكرة
Skip counter كـ alert مش logكام skip في الـ run طبيعي. مئات الـ skips في الـ epoch = alert جاد: الموديل في regime مش قادر FP16 يشيله. الدرس بيتابع rolling skip rate على ١٠٠٠ step، وفي production يعمل page فوق 5%.
الـ clip threshold في الـ configmax_norm = 1.0 default حديث. اعمل sweep على موديل صغير، وحطه في نفس الـ YAML/JSON بتاع الـ schedule.
الـ norm log في CSV مع الـ scheduleالأعمدة الثمانية في ملف واحد، عشان المراجع يشوف schedule + gradient + scale + skip في صف واحد.
scaler.update() كل stepحتى على الـ skip (للمسار اللي عدّى backward)، وإلا المعامل ما بيتغيّرش.

قواعد الاستخدام

  • الـ autocast device يطابق الـ optimizer device: "cuda" للـ GPU و"cpu" للـ CPU. الخلط بيطلّع type error صامت: loss curve شكلها تمام والموديل مش بيتعلم.
  • فحص الـ loss قبل الـ backward: torch.isfinite(loss).all() عملية reduction واحدة رخيصة، وتوفّر step كامل لو الـ loss NaN. اعملها دايمًا.
  • zero_grad(set_to_none=True): بيحط الـ gradients على None بدل الصفر، فالـ optimizer يتخطى الحساب للـ param groups اللي ما اتأثرتش. تحسين throughput مجاني وبيقلل مساحة البجات.

Milestone 1: فحص NaN/Inf وحساب الـ norm

import math, torch

def has_non_finite_grad(parameters):
    for param in parameters:
        if param.grad is None:
            continue
        if not torch.isfinite(param.grad.detach()).all().item():
            return True                     # لقينا NaN أو Inf
    return False

def compute_global_l2_norm(parameters):
    squared_sum = 0.0
    for param in parameters:
        if param.grad is None:
            continue
        squared_sum += float(param.grad.detach().pow(2).sum().item())
    return math.sqrt(squared_sum)           # norm واحد لكل الـ gradients

Check: حط float("inf") في gradient واحد وتأكد إن has_non_finite_grad بترجّع True. وقارن compute_global_l2_norm بـ clip_grad_norm_(params, float("inf")).

Milestone 2: الـ clip بيرجّع (pre, post)

def clip_global_l2_norm(parameters, max_norm):
    if max_norm <= 0:
        raise ValueError("max_norm must be positive")
    pre_clip = compute_global_l2_norm(parameters)
    if not math.isfinite(pre_clip):
        return pre_clip, pre_clip           # NaN/Inf: ما نقصّش، الـ loop هيتخطى
    if pre_clip <= max_norm:
        return pre_clip, pre_clip           # مفيش حاجة تتقصّ
    scale = max_norm / (pre_clip + 1e-12)
    for param in parameters:
        if param.grad is not None:
            param.grad.detach().mul_(scale) # in-place
    return pre_clip, max_norm

Check (ده تمرين ٣): لما الـ norm الأصلي أقل من max_norm الاتنين لازم يتساووا ومفيش gradient اتغيّر. ولما يكون أكبر، compute_global_l2_norm بعد القص لازم يطلع ≈ max_norm.

Milestone 5: الـ rolling skip rate والـ CSV

def rolling_skip_rate(log, window=1000):
    if window <= 0:
        raise ValueError("window must be positive")
    rates, skipped = [], []
    for row in log:
        skipped.append(1 if row.skipped else 0)
        if len(skipped) > window:
            skipped = skipped[-window:]          # نافذة متحركة
        rates.append(sum(skipped) / len(skipped))
    return rates

  • تنسى إن norm = NaN/Inf مش بيتقصّ: الـ clip_global_l2_norm في الدرس بيرجّع الـ norm زي ما هو في الحالة دي. الـ skip هو اللي بيحمي الـ weights، مش الـ clipping.
  • «إحنا بنقصّ في كل step»: لو grad_l2_pre_clip فوق max_norm في معظم الـ steps، يبقى الـ clip بقى جزء من الـ optimizer فعليًا والـ lr الفعلي أصغر من المخطط. شوف الـ lr أو الـ initialization.
  • الـ skip rate بدل الـ skip الواحد: الـ skip النادر طبيعي (الـ scaler بيجرّب مداه). الـ rate العالي هو الإنذار.
  • BF16 بدل FP16 لما الـ skips كتير: المدى الأوسع بيشيل صنف الـ overflow كله، على حساب دقة أقل في الـ mantissa.
  • فين بيظهر: تدريب أي LLM كبير على GPU تقريبًا بيستخدم mixed precision (غالبًا BF16 في الأجهزة الحديثة) وgradient clipping عند 1.0. وأول حاجة بتبصّ عليها لما run ينهار هي الـ grad norm والـ skip log.
