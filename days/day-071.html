تسخين ٥ دقايق: فاكر امبارح؟

امبارح كان عن الـ Edge Deployment. جاوب في دماغك الأول وبعدين افتح الإجابة.

  1. إيه التلات «ميزانيات» (budgets) اللي بتحدد ship ولا no-ship لموديل على جهاز صغير؟
    الإجابةالـ latency (ملّي ثانية لكل صورة)، والـ memory (أقصى استهلاك بالـ MB)، والـ power (طاقة لكل inference).
  2. إيه التلات «مقابض» (knobs) اللي بتصغّر الموديل وتسرّعه؟
    الإجابة(١) اختيار architecture أصغر بنفس الـ recipe، (٢) الـ quantisation يعني INT8 بدل FP32، (٣) الـ runtime زي ONNX Runtime أو TensorRT أو Core ML أو TFLite.
  3. ليه بنقيس الأول قبل ما نحسّن، وإيه حد الخسارة المقبول في الدقة بعد INT8؟
    الإجابةلأنك مينفعش تحسّن اللي مش بتقيسه. والهدف إن الدقة تنزل أقل من 1% بعد الـ quantisation.

01

المشكلة: المنتج سلسلة موديلات مش موديل

موديل واحد مفيد، لكن المنتجات الحقيقية سلاسل منهم:

  • Retail shelf audit: detector + product classifier + price OCR.
  • العربية ذاتية القيادة: 2D detector + 3D detector + segmenter + tracker + planner.
  • فحص طبي مبدئي: segmenter + region classifier + واجهة للدكتور.

كل وصلة بين موديلين هي مكان جديد للـ bugs: coordinate transform، normalisation، resize للماسك. أخطر حاجة إن الغلطة دي صامتة: الكود بيشتغل وبيرجّع أرقام غلط. والـ pipeline قوته بقد أضعف وصلة فيه.

تشبيه: فكّر في خط إنتاج مصنع. كل ماكينة كويسة لوحدها، بس لو ماكينة بتطلّع القطعة بمقاس مقلوب والتانية متوقعة المقاس العادي، الخط كله بيطلّع خردة من غير ما أي إنذار يرن. الـ data contract هو جهاز الفحص اللي بين كل ماكينتين.

الـ capstone ده بيبني الحد الأدنى من pipeline حقيقي: detection + classification + structured output + serving. وأي حاجة تانية في الـ Phase (YOLOv8 بدل Mask R-CNN، OCR head، segmentation branch، tracker) بتتحط في نفس الهيكل. الـ architecture ثابت والقطع بتتبدّل.

02

الـ pipeline: سبع مراحل

الطلب بيعدّي على سبع محطات: فك الصورة وتجهيزها، الـ detector، قص كل detection وتصغيره، الـ classifier، تجميع النتايج، التحقق بـ Pydantic، وبعدين الـ JSON. موديلين بس تقال ومكلفين، والخمس مراحل التانيين هما المكان اللي الـ bugs بتعيش فيه.

معمل ١: امشي مع طلب جوه الـ pipeline

دوس «اللي بعدها» وشوف أنهي مرحلة بتنوّر. الخطوات الأخيرة بتوريك مسارين: النجاح، والفشل (صورة بايظة بترجع 400 على طول).

لاحظ: الـ classifier بياخد crops مش الصورة كلها، وكل crop لازم يتحجّم لنفس المقاس (224×224). ده المكان اللي بيحصل فيه أكتر bugs: الـ clamp، والحجم الصغير، وترتيب الأبعاد.
03

Data contracts: خلّي الغلط يصوّت

كل حدّ بين مرحلتين بيبقى object بنوع (typed). ده بيحوّل الفشل الصامت لفشل عالي الصوت. المستخدم هنا Pydantic.

Detection(box=(x1,y1,x2,y2) بالبكسل، score∈[0,1]، class_id≥0، mask_rle اختياري)
PipelineResult(image_id، detections، classifications، inference_ms)

مثال: لو detector رجّع الصناديق بصيغة (cx, cy, w, h) والمرحلة اللي بعده متوقعة (x1, y1, x2, y2)، من غير contract هتلاقي الـ crop رجع فاضي ومحدش عارف ليه. ومع الـ contract (أو أي validation على الحدود) بتعرف في نفس اللحظة. الـ validation بيكلّف ميكروثواني، ويوفّر ساعات debugging.

معمل ٢: صندوق detection يعدّي ولا يتخطى؟

الصورة حجمها W×H. حرّك الصندوق خلّيه يطلع برا الصورة، وغيّر min_crop. الأداة بتعمل نفس اللي في run(): clamp، وبعدين تحسب حجم الـ crop، وتقول هل هيروح للـ classifier أو يتخطّى.

جرّب: خلّي x2 أكبر من عرض الصورة. الـ clamp بيقصّه. وخلّي الصندوق صغير (عرضه 10) وشوف الـ detection بيفضل في الرد بس من غير classification.
04

الوقت بيروح فين؟ التلات حقائق

  1. الـ preprocessing غالبًا أكبر بلوك لوحده (خصوصًا من غير GPU): فك JPEG، تحويل ألوان، resize. كلها CPU وسهل تنساها.
  2. الـ detector بياخد 70-90% من وقت الـ GPU.
  3. الـ postprocessing (NMS، RLE encode/decode) رخيص على GPU وغالي على CPU. قيس دايمًا على الجهاز الهدف.

معرفة التوزيع ده بتحوّل «عايز أسرّع» لقايمة أولويات. الأرقام النموذجية من الدرس على CPU: preprocess حوالي 3ms، detect من 300 لـ 500ms، classify من 20 لـ 40ms، المجموع من 350 لـ 550ms. على GPU الـ detect بينزل لـ 20-40ms وساعتها الـ preprocess والـ classify بيبانوا أكتر في النسبة.

معمل ٣: مين الـ bottleneck؟

الأعمدة أرقام تقريبية مبنية على المدى اللي في الدرس (مش قياس حقيقي على جهازك). حرّك «تسريع الـ GPU للـ detector» وشوف النسبة بتتغير. بعدها حرّك «عدد الـ detections» وشوف الـ classify بيكبر.

الدرس: بعد ما الـ detector يتسرّع، المرحلة التانية الأكبر هي اللي تستاهل الشغل. الأدوات بتتغير والـ bottleneck بيتحرك.

الـ pipeline الإنتاجي بيتعامل مع كل فشل من غير try/except عام بيخبّي المشكلة. كل فشل له رد محدد:

06

الـ Batching: مقايضة throughput بـ latency

الخدمة الحقيقية بتخدّم ناس كتير في نفس الوقت. لو جمّعت الـ crops من أكتر من طلب في forward pass واحد، الـ throughput بيزيد جامد. الثمن: كل طلب بيستنى لحد ما الـ batch يتملى. الإعداد المعتاد: اجمع الطلبات لحد 20ms، شغّلهم مع بعض، ووزّع الردود. torchserve وTriton بيعملوا ده جاهز، والخدمات الصغيرة بتكتب micro-batcher بسيط لوحدها.

تشبيه: الأتوبيس مقابل التاكسي. الأتوبيس بيستنى لحد ما يتملى (ناقل أكتر ناس في الساعة، بس كل واحد بيستنى)، والتاكسي بيمشي على طول (أسرع لكل واحد، بس عدد أقل في الساعة).

معمل ٣ ب: حاسبة الـ batching (نموذج مبسّط مني)

الحسبة دي تقريب بسيط: الـ batch المتوقع = الطلبات في النافذة. الـ forward لـ batch فيه تكلفة ثابتة وتكلفة لكل صورة. غيّر النافذة ومعدل الطلبات وشوف إمتى الـ batching بيكسب وإمتى بيخسر.

خطوة ١: الـ data contracts

from pydantic import BaseModel, Field
from typing import List, Optional, Tuple

class Detection(BaseModel):
    box: Tuple[float, float, float, float]   # (x1, y1, x2, y2) بالبكسل
    score: float = Field(ge=0, le=1)         # لازم بين 0 و 1
    class_id: int = Field(ge=0)
    mask_rle: Optional[str] = None           # الماسك لو موجود

class Classification(BaseModel):
    detection_index: int                     # بيشاور على أنهي detection
    class_id: int
    class_name: str
    score: float = Field(ge=0, le=1)

class PipelineResult(BaseModel):
    image_id: str
    detections: List[Detection]
    classifications: List[Classification]
    inference_ms: float

خمس ثواني كود بتوفر ساعة debugging في أي pipeline جدي.

خطوة ٢: كلاس Pipeline (الجزء الأول)

import time
import numpy as np
import torch
import torch.nn.functional as F

class VisionPipeline:
    def __init__(self, detector, classifier, class_names, device="cpu", min_crop=32):
        self.detector = detector.to(device).eval()      # eval: بدون dropout/BN training
        self.classifier = classifier.to(device).eval()
        self.class_names = class_names
        self.device = device
        self.min_crop = min_crop                        # أصغر crop نقبله

    def preprocess(self, image):
        # PIL أو numpy (H, W, 3) uint8  ->  tensor (3, H, W) float في [0,1]
        tensor = torch.from_numpy(image).permute(2, 0, 1).float() / 255.0
        return tensor.to(self.device)

    @torch.no_grad()                                    # مفيش gradients في الـ inference
    def detect(self, image_tensor):
        return self.detector([image_tensor])[0]         # الـ detector بياخد list

    @torch.no_grad()
    def classify(self, crops):
        if len(crops) == 0:                             # مفيش crops؟ رجّع list فاضية
            return []
        batch = torch.stack(crops).to(self.device)      # كل الـ crops في batch واحد
        probs = self.classifier(batch).softmax(-1)
        scores, cls = probs.max(-1)
        return list(zip(cls.tolist(), scores.tolist()))

لاحظ @torch.no_grad() و.eval(): من غيرهم الـ inference بيستهلك ميموري على الفاضي ونتايج الـ dropout/BatchNorm بتبقى غلط.

خطوة ٣: دالة run (الجزء التاني)

    def run(self, image, image_id="anonymous"):
        t0 = time.perf_counter()
        tensor = self.preprocess(image)
        det = self.detect(tensor)

        crops, detections, valid_indices = [], [], []
        for i, (box, score, cls) in enumerate(zip(det["boxes"], det["scores"], det["labels"])):
            x1, y1, x2, y2 = [max(0, int(b)) for b in box.tolist()]   # مفيش سالب
            x2 = min(x2, tensor.shape[-1])                            # clamp للعرض
            y2 = min(y2, tensor.shape[-2])                            # clamp للارتفاع
            detections.append(Detection(box=(x1, y1, x2, y2),
                                        score=float(score), class_id=int(cls)))
            if (x2 - x1) < self.min_crop or (y2 - y1) < self.min_crop:
                continue                                              # crop صغير؟ نتخطاه
            crop = tensor[:, y1:y2, x1:x2]
            crop = F.interpolate(crop.unsqueeze(0), size=(224, 224),
                                 mode="bilinear", align_corners=False)[0]
            crops.append(crop)
            valid_indices.append(i)

        class_preds = self.classify(crops)
        classifications = []
        for valid_idx, (cls_id, cls_score) in zip(valid_indices, class_preds):
            classifications.append(Classification(
                detection_index=valid_idx, class_id=int(cls_id),
                class_name=self.class_names[cls_id], score=float(cls_score)))

        return PipelineResult(image_id=image_id, detections=detections,
                              classifications=classifications,
                              inference_ms=(time.perf_counter() - t0) * 1000)

كل وصلة typed، وكل حالة فشل ليها قرار واضح: clamp للصندوق، وتخطّي الـ crop الصغير، ورقم الـ detection محفوظ عشان الـ classification يرجع لصاحبه (detection_index).

خطوة ٥: خدمة FastAPI

from fastapi import FastAPI, UploadFile, HTTPException
from io import BytesIO
from PIL import Image

app = FastAPI()
pipe = None                                   # هيتحمّل وقت الـ startup

@app.on_event("startup")
def load():                                   # لو الموديل وقع، السيرفس تقع هنا مش عند أول request
    global pipe
    detector = maskrcnn_resnet50_fpn_v2(weights="DEFAULT").eval()
    classifier = convnext_tiny(weights="DEFAULT").eval()
    pipe = VisionPipeline(detector, classifier, class_names=[f"c{i}" for i in range(1000)])

@app.post("/detect")
async def detect_endpoint(file: UploadFile):
    if file.content_type not in {"image/jpeg", "image/png", "image/webp"}:
        raise HTTPException(status_code=400, detail="unsupported image type")
    data = await file.read()
    try:
        img = Image.open(BytesIO(data)).convert("RGB")
    except Exception:
        raise HTTPException(status_code=400, detail="cannot decode image")   # 400 مش 500
    result = pipe.run(np.asarray(img), image_id=file.filename or "upload")
    return result.model_dump()

خطوة ٦: الـ benchmark

def benchmark(pipe, num_runs=20, image_size=(400, 600)):
    img = (np.random.rand(*image_size, 3) * 255).astype(np.uint8)
    pipe.run(img)                                    # warm-up: أول مرة دايمًا أبطأ
    stages = {"preprocess": [], "detect": [], "classify": [], "total": []}
    for _ in range(num_runs):
        t0 = time.perf_counter()
        tensor = pipe.preprocess(img)
        t1 = time.perf_counter()
        det = pipe.detect(tensor)
        t2 = time.perf_counter()
        crops = []
        for box in det["boxes"]:
            x1, y1, x2, y2 = [max(0, int(b)) for b in box.tolist()]
            x2 = min(x2, tensor.shape[-1]); y2 = min(y2, tensor.shape[-2])
            if (x2 - x1) >= pipe.min_crop and (y2 - y1) >= pipe.min_crop:
                crop = tensor[:, y1:y2, x1:x2]
                crop = F.interpolate(crop.unsqueeze(0), size=(224, 224),
                                     mode="bilinear", align_corners=False)[0]
                crops.append(crop)
        pipe.classify(crops)
        t3 = time.perf_counter()
        stages["preprocess"].append((t1 - t0) * 1000)
        stages["detect"].append((t2 - t1) * 1000)
        stages["classify"].append((t3 - t2) * 1000)
        stages["total"].append((t3 - t0) * 1000)
    for stage, times in stages.items():
        times.sort()                                  # نرتب عشان نجيب p50 و p95
        print(f"{stage:12s} p50={times[len(times)//2]:7.1f} ms  p95={times[int(len(times)*0.95)]:7.1f} ms")

الـ warm-up ضروري. وعلى GPU لازم تعمل torch.cuda.synchronize() بين المراحل عشان القياس يبقى صح، لأن الـ GPU شغّال بشكل غير متزامن (نسخة main.py في الريبو بتعمل sync لـ cuda وmps). الأرقام النموذجية على CPU اتذكرت فوق.

للإنتاج: إيه اللي بيتضاف

  • Model versioning: سجّل اسم الموديل وhash الأوزان في كل رد.
  • Trace ID لكل request: سجّل وقت كل مرحلة عشان تربط الطلب البطيء بالمرحلة المسؤولة.
  • Fallback: لو الـ classifier عدّى الوقت، رجّع الـ detections من غير classifications بدل ما تفشّل الطلب كله.
  • Safety filters: فلاتر NSFW أو PII بعد الـ classification وقبل ما الرد يطلع.
  • Batch endpoint: /detect_batch بياخد list روابط صور للمعالجة بالجملة.

للإنتاج الحقيقي: torchserve وTriton Inference Server وBentoML بيدّوك batching وversioning وmetrics وhealth checks جاهزين. FastAPI مباشرة كويس للنماذج الأولية والمنتجات الصغيرة. ومن مخرجات الدرس في الريبو: prompt بيراجع شكل الـ service ويسمّي أول bug، وskill بيوزّع ميزانية الوقت على مراحل الـ pipeline.

التمارين

  1. (سهل) شغّل الـ pipeline على 10 صور من أي dataset مفتوح. اطلّع متوسط وقت كل مرحلة وتوزيع عدد الـ detections لكل صورة.
    تلميحاستخدم benchmark كأساس، بس بدل الصورة العشوائية اقرا الصور بـ PIL.Image.open(path).convert("RGB") وحوّلها np.asarray. خزّن len(result.detections) في list واطبع collections.Counter عليها.
  2. (متوسط) ضيف حقل ماسك في Detection وشفّره RLE. اتأكد إن الـ JSON أقل من 1MB حتى لصورة فيها 10 objects.
    تلميحالـ mask_rle موجود أصلًا كـ Optional[str]. الـ RLE بيخزّن «طول التكرار» بدل كل بكسل، فالماسكات الكبيرة المتصلة بتتضغط جامد. اقيس len(result.model_dump_json()) وقارنه بـ 1,000,000. لو كبر، قلّل دقة الماسك قبل التشفير.
  3. (صعب) ضيف micro-batcher قدام الـ classifier: يجمّع الـ crops لحد 10ms ويعملها كلها في نداء GPU واحد ويرجّع لكل طلب نتيجته. قيس الـ throughput عند 5 طلبات متزامنة في الثانية والـ latency اللي زادت.
    تلميحاستخدم asyncio.Queue: كل طلب يحط crops مع asyncio.Future، وtask خلفي يستنى أول عنصر وبعدها ينام 10ms ويسحب كل اللي في الـ queue، يعمل torch.stack ويشغّل الـ classifier مرة واحدة، وبعدها يقسّم النتايج حسب الـ Future. توقّع إن الـ latency تزيد بحد أقصى حوالي 10ms والـ throughput يزيد.
  4. إضافة مني · اكتب الـ contract اللي يمسك الغلط: غيّر الـ Detection بحيث يرفض أي صندوق فيه x2 <= x1 أو y2 <= y1 باستخدام @model_validator من Pydantic، وبعدها جرّب تدّيه (cx, cy, w, h).
    تلميح وإجابةجوه الـ validator خد self.box، اعمل unpack لـ 4 قيم، وraise ValueError("box must be x1,y1,x2,y2 with x2>x1 and y2>y1") لو الشرط اتكسر. صندوق مدخل بصيغة (cx,cy,w,h) غالبًا هيعدّي لو w وh أكبر من cx وcy، فاعتبره تمرين: الـ validation لوحده مش بيمسك كل الأنواع، فضيف كمان تحقق إن الصندوق جوه حدود الصورة، وسجّل صيغة الصندوق في اسم الحقل.
10

إضافة مني: أخطاء هتقع فيها، وفين بتظهر في الـ LLMs والـ agents

  • RGB مقابل BGR: OpenCV بيقرا الصور BGR وPIL وtorchvision بيتوقعوا RGB. الكود هيشتغل والدقة هتنزل من غير سبب واضح. اعمل check على الحدود.
  • إحداثيات قبل وبعد الـ resize: لو الـ detector اشتغل على صورة اتصغّرت، لازم ترجّع الصناديق لمقاس الصورة الأصلية قبل الـ crop، وإلا القص هيكون في مكان غلط.
  • ترتيب الأبعاد: الصورة numpy شكلها (H, W, 3) والـ tensor (3, H, W). نسيان permute بيكسر الشكل أو يديك نتايج غريبة.
  • القياس من غير warm-up: أول نداء بيحمّل kernels وبيبطّأ. ولو قست على GPU من غير synchronize هتقيس وقت «الإطلاق» مش وقت الشغل.
  • الـ p95 مش المتوسط: المستخدم بيحس بالطلب البطيء مش بالمتوسط. دايمًا بلّغ p50 وp95.
  • في الـ LLMs والـ agents: نفس الفكرة بالظبط. الـ tool calling بيستخدم JSON schema كـ contract بين الـ LLM والأداة، والـ structured output بيتحقق بـ Pydantic. ولو الأداة رجّعت شكل غلط، الـ agent بيكمل على بيانات بايظة ويطلّع إجابة واثقة وغلط. وبعض الأنظمة بتخلّي موديل لغة يقرا crops من detector، يعني pipeline متعدد الموديلات برضه.
