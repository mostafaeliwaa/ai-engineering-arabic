تسخين ٥ دقايق: فاكر امبارح؟

جاوب في دماغك الأول، وبعدين افتح الإجابة.

  1. سؤال فيه اسم فنكشن حرفي زي AbortMultipartOnFail. مين هيكسب: BM25 ولا الـ dense؟ وسؤال متصاغ بكلام تاني خالص؟
    الإجابةالاسم الحرفي: BM25 بيكسب لأن الكلمة موجودة بالنص في الـ corpus. السؤال المتصاغ بكلام تاني ("how do we handle cancelled uploads"): الـ dense بيكسب لأنه بيفهم المعنى من غير ما الكلمات تتطابق.
  2. معادلة الـ RRF إيه، وليه k = 60؟
    الإجابةلكل مستند بنجمع 1 / (k + rank) من كل لستة. مع k = 60 الأول بياخد 1/61 والعاشر 1/70، يعني المساهمة بتقل ببطء والمرشحين اللي تحت لسه "بيصوّتوا".
  3. ليه مينفعش نعمل alpha * bm25 + (1 − alpha) * cosine وخلاص؟
    الإجابةلأن سكور BM25 ملوش سقف وبيتغير مع الـ corpus، والـ cosine بين −1 و1. الـ alpha لازم يتظبط لكل corpus ويبوظ مع كل reindex. الـ ranks بقى ممكن تتقارن بين الطريقتين، عشان كده RRF أثبت.

النهاردة بناخد الـ top-N اللي طلع من الـ hybrid retriever ده، ونعيد ترتيبهم بموديل أذكى.

المشكلة: الـ bi-encoder أعمى عن السؤال

الـ bi-encoder (اللي هو الـ vector retriever العادي) بيحوّل السؤال لمتجه، وكل مستند لمتجه، كل واحد لوحده، وبعدين يرتّب بالـ cosine. المستند ما شافش السؤال أبدًا وهو بيتحوّل لمتجه. يعني الموديل لازم يكبس كل حاجة مهمة في المستند في متجه واحد، من غير ما يعرف هيتسأل عن إيه.

ده سريع جدًا: embedding واحد لكل مستند وقت الـ indexing، وواحد للسؤال وقت السؤال. وهو الطريقة الوحيدة اللي تنفع ترتّب بيها corpus كامل.

التمن: الدقة. مستندين عن نفس الموضوع العام ممكن يطلعلهم متجهين شبه بعض، مع إن واحد بس فيهم بيجاوب السؤال فعلًا. الـ bi-encoder مش هيعرف يفرّق.

الـ cross-encoder بيحل ده: بيقرا السؤال والمستند مع بعض كسلسلة واحدة [query] [SEP] [document]، ويعمل full attention على الاتنين، ويطلّع رقم واحد للصلة. كل token في المستند يقدر يبص على كل token في السؤال.

التمن هنا: السرعة. لازم forward pass لكل زوج (سؤال، مستند). corpus فيه ١٠ مليون مستند = ١٠ مليون forward pass لكل سؤال. مستحيل في وقت request.

تشبيه: الـ bi-encoder زي موظف HR بيفرز ألف CV من الملخص اللي في أول سطر بس، كل CV اتكتب قبل ما الوظيفة تتعلن. سريع، بس ممكن يغلط بين اتنين ملخصهم شبه بعض. الـ cross-encoder زي إنك تعمل انترفيو حقيقي: بتقعد مع المرشح وبتسأله عن الوظيفة دي بالذات. أدق بكتير، بس مينفعش تعمل انترفيو لألف واحد. فبتفرز بالـ CV الأول، وتعمل انترفيو لأحسن ٢٠ بس.

ومعاها سلسلة تانية اسمها type ids بتقول كل token تبع مين: 0 للسؤال و1 للمستند. في كود الدرس الـ [CLS] وأول [SEP] بياخدوا 0، والمستند وآخر [SEP] بياخدوا 1، والـ padding بياخد 0.

في الآخر محتاجين رقم واحد. فيه طريقتين:

  • CLS head: خد الخرج اللي عند مكان [CLS] ودخّله في linear layer واحدة تطلّع رقم.
  • Mean-pooling head: خد متوسط خرج آخر layer على كل الأماكن اللي مش padding، ودخّله في linear layer. ده اللي الدرس بيستخدمه. الفرق بين الطريقتين صغير.

الحل: مرحلتين، retrieve وبعدين rerank

بدل ما تختار بين السريع والذكي، استخدم الاتنين ورا بعض:

Query + Corpus → Bi-Encoder → Top-N → Cross-Encoder (+Query) → Top-K
  1. الـ bi-encoder (أو الـ hybrid بتاع امبارح) يجيب N مرشح من الـ corpus كله. N صغير: من ٥٠ لـ ٢٠٠.
  2. الـ cross-encoder يقرا كل زوج (السؤال، المرشح) ويدي سكور، ونرتّب ونحتفظ بأحسن K.

النتيجة: الوقت الكلي بيفضل جوه ميزانية الـ request، والجودة بقت جودة الـ cross-encoder. بس فيه سقف مهم:

القاعدة الذهبية: الـ cross-encoder مش ممكن يرفع الـ recall فوق recall الـ bi-encoder عند N. لو الإجابة الصح مش في الـ N مرشح، الـ reranker عمره ما هيشوفها. عشان كده N صغير أوي = سقف للجودة، مش بس توفير وقت.

معمل ٢: القُمع وحساب الوقت

حرّك حجم الـ corpus وN وK. هتشوف الوقت لو شغّلت الـ cross-encoder على الـ corpus كله، مقابل الـ two-stage، مقارنةً بميزانية الـ request.

وبدّل الـ batching: الـ reranker الحقيقي بيشغّل الـ N مرشح في batch واحد (في الكود ده _batch_encode). من غيره الوقت بيتضرب في N.

ليه الدرس بيدرّب موديل صغير؟

الـ cross-encoder الحقيقي هو encoder transformer اتعمله fine-tune. في الـ production بتحمّل checkpoint وتشغّله. هنا الهدف إنك تشوف شكل الموديل وشكل منحنى الـ latency-quality، مش إنك تدرّب ranker عالمي.

فبنبني nn.Module صغير فيه: embeddings، transformer block واحد بـ multi-head attention (٤ heads)، و regression head واحدة. والـ initialization ثابتة من seed، فالديمو بيطلع نفس النتيجة كل مرة من غير weights على الديسك.

الموديل الصغير ده بيتعلم "الشكل الصح" من الـ fixture: الأزواج المرتبطة بتاخد سكور أعلى من غير المرتبطة، والـ top-k بعد الـ rerank بيتماشى مع الـ labels.

خطوة ١: الـ tokenizer اللي بيحزم الزوج

import math, re, time
from dataclasses import dataclass, field
import numpy as np
import torch
import torch.nn as nn

VOCAB_SIZE = 8192
PAD_ID, SEP_ID, CLS_ID = 0, 1, 2      # أول 3 ids محجوزين
SEED = 19660101

def _set_seed(seed=SEED):
    torch.manual_seed(seed)
    np.random.seed(seed)

def _token_to_id(token):
    h = 0
    for ch in token:                  # hash ثابت لكل كلمة
        h = (h * 1315423911) ^ ord(ch)
        h &= 0xFFFFFFFF
    return 3 + (h % (VOCAB_SIZE - 3)) # بعد الـ ids المحجوزة

_WORD = re.compile(r"[a-z0-9]+")

def tokenize_pair(query, document, max_len=96):
    q = [_token_to_id(t) for t in _WORD.findall(query.lower())]
    d = [_token_to_id(t) for t in _WORD.findall(document.lower())]
    ids = [CLS_ID] + q + [SEP_ID] + d + [SEP_ID]
    type_ids = [0] * (len(q) + 2) + [1] * (len(d) + 1)   # 0 سؤال، 1 مستند
    if len(ids) > max_len:            # قص من الآخر
        ids, type_ids = ids[:max_len], type_ids[:max_len]
    else:                             # كمّل بـ PAD
        pad = max_len - len(ids)
        ids += [PAD_ID] * pad
        type_ids += [0] * pad
    return ids, type_ids

خطوة ٢: الموديل نفسه

class CrossEncoder(nn.Module):
    def __init__(self, d_model=64, n_heads=4, ff_hidden=128, max_len=96):
        super().__init__()
        _set_seed()                                   # نفس الأوزان كل مرة
        self.token_emb = nn.Embedding(VOCAB_SIZE, d_model, padding_idx=PAD_ID)
        self.type_emb = nn.Embedding(2, d_model)      # سؤال ولا مستند
        self.pos_emb = nn.Embedding(max_len, d_model) # المكان
        self.attn = nn.MultiheadAttention(d_model, n_heads, batch_first=True)
        self.ln1 = nn.LayerNorm(d_model)
        self.ff = nn.Sequential(nn.Linear(d_model, ff_hidden), nn.GELU(),
                                nn.Linear(ff_hidden, d_model))
        self.ln2 = nn.LayerNorm(d_model)
        self.head = nn.Linear(d_model, 1)             # رقم واحد
        self.max_len = max_len

    def forward(self, input_ids, type_ids):
        batch, seq = input_ids.shape
        pos = torch.arange(seq, device=input_ids.device).unsqueeze(0).expand(batch, seq)
        x = self.token_emb(input_ids) + self.type_emb(type_ids) + self.pos_emb(pos)
        mask = (input_ids == PAD_ID)                  # True = متبصّش هنا
        attn_out, _ = self.attn(x, x, x, key_padding_mask=mask)
        x = self.ln1(x + attn_out)                    # residual + norm
        x = self.ln2(x + self.ff(x))
        keep = (~mask).unsqueeze(-1).float()          # mean-pool من غير PAD
        pooled = (x * keep).sum(dim=1) / keep.sum(dim=1).clamp(min=1.0)
        return self.head(pooled).squeeze(-1)          # shape: (batch,)

خطوة ٣: الـ batching والتدريب

@dataclass
class Triple:
    query: str
    document: str
    label: float          # 1.0 مرتبط، 0.0 مش مرتبط (وفيه درجات بينهم)

def _batch_encode(pairs, max_len=96):
    ids, tids, labels = [], [], []
    for p in pairs:
        i, t = tokenize_pair(p.query, p.document, max_len)
        ids.append(i); tids.append(t); labels.append(p.label)
    return (torch.tensor(ids, dtype=torch.long),
            torch.tensor(tids, dtype=torch.long),
            torch.tensor(labels, dtype=torch.float))

def train_tiny(model, triples, epochs=60, lr=5e-3):
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    loss_fn = nn.MSELoss()                # regression على الـ label
    losses = []
    ids, tids, labels = _batch_encode(triples, max_len=model.max_len)
    for _ in range(epochs):               # full batch كل epoch
        opt.zero_grad()
        loss = loss_fn(model(ids, tids), labels)
        loss.backward()
        opt.step()
        losses.append(loss.item())
    return losses

خطوة ٤: واجهة الـ rerank

@dataclass
class Candidate:
    doc_id: str
    text: str
    retriever_score: float = 0.0

def rerank(model, query, candidates, top_k=5):
    if not candidates:
        return []
    model.eval()
    triples = [Triple(query, c.text, 0.0) for c in candidates]  # السؤال الأول دايمًا
    ids, tids, _ = _batch_encode(triples, max_len=model.max_len)
    with torch.no_grad():                                       # forward واحد للـ N كلهم
        scores = model(ids, tids).tolist()
    out = sorted(zip(candidates, scores), key=lambda x: -x[1])
    return out[:top_k]

خطوة ٥: الـ bi-encoder الوهمي والـ pipeline

def mock_embed(text, dim=96):
    vec = [0.0] * dim
    for tok in _WORD.findall(text.lower()):
        h = 0
        for ch in tok:
            h = (h * 1315423911) ^ ord(ch)
            h &= 0xFFFFFFFF
        vec[h % dim] += 1.0              # كل كلمة بتزود خانتين
        vec[(h >> 7) % dim] += 0.5
    norm = math.sqrt(sum(v * v for v in vec)) or 1.0
    return [v / norm for v in vec]       # طول 1 → الـ dot = cosine

def cosine(a, b):
    return sum(x * y for x, y in zip(a, b))

@dataclass
class BiEncoder:
    docs: list = field(default_factory=list)
    vectors: list = field(default_factory=list)
    def add(self, c):
        self.docs.append(c); self.vectors.append(mock_embed(c.text))  # وقت الـ indexing
    def search(self, query, top_n):
        qv = mock_embed(query)
        scored = sorted(((d, cosine(qv, v)) for d, v in zip(self.docs, self.vectors)),
                        key=lambda x: -x[1])
        return [Candidate(d.doc_id, d.text, retriever_score=s) for d, s in scored[:top_n]]

def pipeline(query, retriever, reranker, top_n=10, top_k=5):
    t0 = time.perf_counter()
    cands = retriever.search(query, top_n)          # المرحلة ١: رخيصة
    t1 = time.perf_counter()
    reranked = rerank(reranker, query, cands, top_k)  # المرحلة ٢: غالية
    t2 = time.perf_counter()
    return {"retrieve_top_n": cands, "reranked_top_k": reranked,
            "latency_retrieve_ms": (t1 - t0) * 1000,
            "latency_rerank_ms": (t2 - t1) * 1000}

خطوة ٦: الـ fixture والديمو

انسخ CORPUS (٨ مستندات d1…d8 عن multipart upload، retry budget، check_permission، policy engine، rank fusion، index sizing، cancelling jobs) وTRAIN_TRIPLES (١٤ triple) من الملف الأصلي، وبعدين:

def main():
    _set_seed()
    retriever = BiEncoder()
    for c in CORPUS:
        retriever.add(c)
    reranker = CrossEncoder()
    losses = train_tiny(reranker, TRAIN_TRIPLES, epochs=60)
    print(f"trained tiny cross-encoder, loss {losses[0]:.4f} -> {losses[-1]:.4f}\n")
    for q in ["how do we abort a multipart upload",
              "centralized authorization check function",
              "how do we cancel a job"]:
        r = pipeline(q, retriever, reranker, top_n=8, top_k=3)
        print("query:", q)
        for c in r["retrieve_top_n"][:5]:

        for c, s in r["reranked_top_k"]:
            print(f"   ce  {c.doc_id}  cross_score={s:.4f}")

المطبيعني إيهتعمل إيه
الـ cross-encoder مش متماثلscore(q, d) ≠ score(d, q). لو بدّلتهم بالغلط الـ recall بيقعالسؤال الأول دايمًا
N صغير يخبّي المشكلةلو N = K الـ reranker يقدر يرتّب الـ K بس، مش يدخّل واحد جديد. الـ recall@K مش هيتحرك والمكسب يبان صفرN ≥ 3 × K على الأقل
داتا التدريب سربت للـ evalلو أسئلة الـ eval جوه الـ triples، الـ rerank هيبان سحرافصل train وeval حتى في fixture
الأوزان تقيلة22M parameter × 4 bytes (float32) = 88MBخطط ذاكرة الـ model server قبل ما توعد بـ p95 أقل من 100ms
الـ batchingمن غيره الوقت بيتضرب في Nشغّل الـ N في batch واحد زي _batch_encode

استخدامه في الـ production

  • ثبّت التلاتة مع بعض: الـ bi-encoder والـ cross-encoder وN. تغيير أي واحد فيهم يبوّظ الـ eval.
  • Cache: خزّن خرج الـ reranker بـ hash لـ (query, document_id). نفس السؤال على corpus ثابت بيترتب نفس الترتيب، والـ cache hit تخفيض latency ببلاش.
  • سجّل سكور الأول: لو أعلى سكور أقل من threshold خاص بالـ corpus، يبقى السؤال غالبًا out-of-domain. قول للـ LLM "أنا مش واثق".

بعد كده: درس ٦٨ بيقيس الـ pipeline ده end to end، ودرس ٦٩ بيحط الـ reranker ده ورا الـ hybrid retriever بتاع امبارح وقدام الـ answer generator.

التمارين

  1. Sweep لـ N من ٥ لـ ٥٠ وارسم recall@1 بعد الـ rerank. لاقي الركبة على الـ fixture.
    تلميحالـ corpus فيه ٨ مستندات بس، فأي N ≥ 8 هو هو. اعمل loop على N in [1..8] ولكل سؤال شوف هل المستند الصح (d1 لـ abort، d4 لـ authorization، d8 لـ cancel) جه الأول. لو عايز منحنى حقيقي كبّر الـ corpus بمستندات distractor.
  2. درّب ١٠ epochs بدل الـ default، وقيس الـ margin بين السكور الموجب والسالب كل epoch.
    تلميحعدّل train_tiny عشان بعد كل opt.step() يحسب في torch.no_grad() متوسط السكور للـ triples اللي label = 1.0 ناقص متوسط اللي label = 0.0. خد بالك إن الـ default في الكود 60 epoch، فقارن 10 مقابل 60.
  3. بدّل الـ mean-pooling بـ CLS head وقارن سرعة التقارب.
    تلميح[CLS] دايمًا في المكان 0، فـ pooled = x[:, 0, :]. ارسم الـ losses للطريقتين على نفس الرسمة.
  4. head تانية بتتوقع binary "هل الإجابة في المستند؟". استخدم واحدة للترتيب وواحدة للـ threshold.
    تلميحزوّد self.answer_head = nn.Linear(d_model, 1) وخلّي forward يرجّع الاتنين. الـ loss = MSE للترتيب + BCEWithLogitsLoss للـ binary. وقت الـ inference: رتّب بالأولى، وارمي أي مرشح sigmoid(answer) < 0.5.
  5. بدّل الـ mock bi-encoder بالـ hybrid retriever من درس ٦٥ ووصّل المرحلتين. قيس تغيّر الـ top-K مقابل الـ bi-encoder لوحده.
    تلميحالـ pipeline محتاج بس object فيه search(query, top_n) بيرجّع Candidate. اعمل wrapper صغير حوالين HybridRetriever يحوّل نتايجه لـ Candidates.
  6. تمرين إضافي مني (شغل حقيقي): اعمل CachedReranker فيه cache بـ hash((query, doc_id))، وقيس الـ latency لنفس السؤال مرتين. وزوّد فلاج low_confidence لو أعلى سكور أقل من threshold، وجرّبه بسؤال ملوش علاقة خالص بالـ corpus زي "best pizza in cairo".
    تلميحفي التاني مرة كل الـ pairs موجودة في الـ dict فمفيش forward pass خالص. الـ threshold مينفعش يتاخد من الهوا: شغّل كل أسئلة الـ fixture وشوف أقل top-1 score للأسئلة اللي ليها إجابة، وحط الـ threshold تحته شوية. ده بالظبط اللي بتعمله في RAG حقيقي قبل ما تقول للـ LLM "مش لاقي".
09

إضافة مني: اللي الدرس مقالهوش

الحتة دي مش من الدرس الأصلي. دي إضافات عشان الصورة تكمل.

الحدس: ليه الـ cross أذكى؟

في الـ bi-encoder، التفاعل الوحيد بين السؤال والمستند هو dot product واحد في الآخر خالص. في الـ cross-encoder، التفاعل بيحصل جوه كل attention layer: كلمة "abort" في السؤال تقدر تمسك في "aborts" في المستند وتشوف هل الجملة دي فعلًا بتجاوب ولا بس بتتكلم في نفس الموضوع.

غلطات شائعة

  • تفتكر السكور احتمال: سكور الـ reranker رقم للترتيب. في الدرس ده regression بالـ MSE، ومش لازم يبقى بين 0 و1. متقارنش سكورات من موديلين مختلفين، ومتحطش threshold من غير ما تقيسه على داتاك.
  • الـ max_len بيقص المستند: لو الـ chunk طويل، الجزء اللي فيه الإجابة ممكن يتقص (زي ما شفت في المعمل ١). ده سبب تاني إن الـ chunking (درس ٦٤) مهم.
  • بتعمل rerank للـ corpus كله "عشان الجودة": ده بالظبط اللي الـ two-stage موجود عشان يمنعه.
  • بتنسى model.eval() وtorch.no_grad(): الكود بيعملهم في rerank عشان الـ inference يبقى أسرع ومن غير gradients.

بيظهر فين في الـ LLMs والـ Agents؟

  • RAG: تقريبًا كل pipeline جاد بيحط reranker بين الـ retriever والـ LLM، عشان الـ context window يتملي بأحسن chunks مش بأكترهم.
  • Agents: لما الـ agent عنده أدوات كتير أو memory كبيرة، نفس الفكرة: retrieve مرشحين بسرعة، وبعدين rerank بموديل أذكى قبل ما تحطهم في الـ prompt.
  • LLM كـ reranker: ممكن تخلي الـ LLM نفسه يرتّب المرشحين. نفس المنطق بالظبط بس أغلى: لازم يشتغل على N صغير بس.
  • Late interaction: فيه طريقة وسط زي ColBERT، بتحتفظ بمتجه لكل token بدل متجه واحد للمستند. أدق من الـ bi وأرخص من الـ cross.
