ليه Subprocess؟ الـ Runner هو ضمير الـ Loop

الـ research loop بيشغّل كود مش مضمون. الـ hypothesis جاية من sampler، والـ script جاي من نفس الطريق. لو شغّلته جوه نفس البروسيس بتاع الـ orchestrator، أول crash أو memory leak أو حلقة لا نهائية هيوقّع الـ orchestrator كله معاه.

تشبيه: تخيّل مطبخ مطعم. لو الطباخ الجديد بيجرّب وصفة في نفس الغاز اللي بيطبخ عليه طلبات الزباين وولّعت، المطبخ كله بيقف. الـ subprocess زي إنك تدّيله بوتاجاز لوحده في أوضة تانية وتفضل ماسك مفتاح الغاز: تقدر تقفل عليه في أي لحظة.

الـ subprocess أبسط عزل بتديه اللغة: بروسيس منفصل، address space مستقل، و«handle» في إيد الأب يقدر يعمل بيه kill. المهم: الدرس ده مش sandbox كامل. مفيش cgroup ولا seccomp ولا namespaces. اللي فيه هو العقد الأساسي اللي أي sandbox أكبر بيبني عليه: wall clock timeout + memory poller + مسار kill لو أي حد فيهم اتخطّى.

الفكرة الكبيرة: «الـ loop مبيبقاش أمين غير بقدر أمانة قياساته». الـ runner لازم يطلّع blob أرقام الـ evaluator يقدر يثق فيه، حتى لو التجربة نفسها اتقتلت أو وقعت.
02

الـ ExperimentSpec والـ ExperimentResult: عقد الدخول والخروج

التجربة بتتوصف كـ spec مكتوب بأنواع (typed)، يقدر الـ runner يحوّله لـ subprocess. وفي الآخر بيرجع result بشكل ثابت. الشكلين دول هما اللي بيربطوا الدروس ٥٠ و٥١ و٥٢ و٥٣ من غير أي glue.

الحقل في الـ Specمعناه
spec_idid ثابت للتجربة، مثلًا exp_001
hypothesis_idرقم بيرجّعك للـ queue بتاعة الدرس ٥٠
script_pathمسار سكربت Python اللي هيتشغّل
configdict بيتبعت للسكربت كملف JSON واحد
seedالـ seed اللي بيخلّي النتايج ثابتة (deterministic)
wall_timeout_sالـ timeout الصلب: لو عدّى، البروسيس بيتقتل
memory_cap_mbالـ cap «الناعم» للذاكرة: بيتعمله polling
metric_keysالحقول اللي الـ evaluator هيقراها من الناتج

الـ runner بيكتب الـ config في ملف مؤقت، والسكربت لازم يطبع سطر JSON واحد على stdout مفاتيحه تشمل كل الـ metric_keys (وأكتر لو حب). أي حاجة تانية على stdout بتتسجّل بس مبتتحسبش كـ metrics.

الحقل في الـ Resultمعناه
exit_codeكود الخروج. الـ runner مبيرميش exception لو مش صفر، بيسجّله بس
terminalواحدة من: ok | timeout | oom | crash
wall_time_sالوقت الفعلي اللي خدته التجربة
peak_rss_mbأعلى استهلاك ذاكرة اتلاحظ (أو None لو المنصة مش بتدعم)
metricsالـ blob النهائي
intermediate_metricsسطور JSON اللي قبل النهائي (لمنحنيات التعلّم)
stdout_tail / stderr_tailآخر جزء من المخرجات والأخطاء
قاعدة مهمة: الـ evaluator بيبص على terminal الأول. لو أي حاجة غير "ok" يبقى التجربة فشلت والحكم أوتوماتيك. ولو ok بس، الأرقام بتعدّي على الـ significance test (درس بكرة).
03

معمل ١: عمر الـ Run من الـ Spec للـ Result

الـ lifecycle بالكامل

الـ runner بيمشي بالترتيب ده: يحوّل الـ config لملف مؤقت، يفتح subprocess، يشغّل timer وmemory poller جنبه، وبعدين يا يتقتل البروسيس (timeout أو oom) يا يخلص ويتقرأ آخر JSON.

دوس «اللي بعدها» وشوف أربع سيناريوهات: نجاح، timeout، oom، crash. لاحظ إن الـ label بيتحدد بترتيب ثابت: oom الأول، بعدين timeout، بعدين exit code.

لاحظ: الـ crash بيتسمّى crash حتى لو السكربت طبع metrics قبل ما يقع. الـ partial run بيتعامل كفشل افتراضيًا.
04

الـ Memory Cap «الناعم» والـ Poller

الـ cap الصلب محتاج resource.setrlimit وبيشتغل على POSIX بس. الدرس بيستخدم طريقة محمولة: thread صغير بيصحى كل poll_interval ويقرا الـ RSS (الذاكرة الفعلية المستخدمة) من /proc/<pid>/status (سطر VmRSS) أو من أمر ps لو مفيش /proc. لو عدّى الـ cap: kill.

اسمه «ناعم» لأن الـ poller بيصحى كل فترة، والبروسيس يقدر يعمل spike فوق الـ cap بين نظرتين وينزل تاني قبل ما يتشاف. الـ runner بيسجّل أعلى RSS اتلاحظ عشان الـ evaluator يعرف كانت قريبة من الحد قد إيه.

ولو المنصة مش بتديك أي طريقة تقرا الـ RSS، الـ poller بيطبع warning مرة واحدة ويقفل نفسه. الـ wall clock timeout يفضل شغال في كل الأحوال. (الدرس فيه اختبارات للمسارين.)

معمل ٢: امسك الـ spike لو تقدر

التجربة بتعمل spike في الذاكرة بيبدأ عند 400ms. النقط على الرسم هي نظرات الـ poller: خضرا = تحت الـ cap، حمرا = فوقه (يعني اتقتل).

صغّر مدة الـ spike وكبّر الـ poll interval، وشوف إزاي الـ spike بيعدّي من غير ما يتشاف. ده بالظبط معنى «soft».

05

تجميع الـ stdout والـ stderr والـ Final Metrics

الـ runner بيقرا الـ pipes بعد ما البروسيس يخلص. الـ stdout بيتفحص سطر سطر: كل سطر بيبدأ بـ { وبيتحوّل JSON صالح (dict) ومفاتيحه تشمل كل الـ metric_keys بيتحسب «covering line». آخر covering line هو الـ metrics النهائي، وكل اللي قبله بيتحط في intermediate_metrics. وده اللي بيدّي الـ evaluator منحنى الـ loss.

الـ stderr بيتحفظ زي ما هو. والـ exit code اللي مش صفر = crash، وكمان صفر من غير metrics = crash (لأن مفيش نتيجة تتصدّق).

تشبيه: زي مراقب لجنة بيجمع كراسات الإجابة: بيقرا الأوراق كلها بالترتيب، وآخر ورقة مكتملة هي الإجابة النهائية، والمسودات اللي قبلها بيحتفظ بيها كدليل.

الـ Ablation: مفتاح واحد في المرة

الـ helper ablate(base, knob, values) بياخد spec أساسي ويرجّع spec لكل قيمة، فيها config[knob] متغيّرة فقط، وspec_id مشتق: f"{base.spec_id}_{knob}_{value}". والـ AblationRunner بيشغّلهم بالترتيب ويرجّع AblationTable مفتاحها قيمة الـ knob.

ليه knob واحد؟ الـ full factorial بيتفجّر أُسّيًا وبيطلّع جدول مش بتعرف تفسّره. مفتاح واحد بيدّيك محور نضيف الـ evaluator يرسمه. ولو عايز أكتر من knob، كرّر ablation لكل واحد وركّبهم بنفسك.

معمل ٣: ablation على k، وتكلفة الـ factorial

الرسم الأول بيحاكي سكربت sparsity_experiment.py (من غير الـ noise): الـ loss بيقل مع الـ steps ومع الـ k. لاحظ إن k فوق 32 مبيفرقش، لأن السكربت بيستخدم min(k, 32).

الحاسبة اللي تحتها بتوريك ليه الـ factorial مش عملي.

الـ Determinism: ليه الـ Seed إجباري

كل spec ليه seed، والـ runner بيمرره للسكربت عن طريق config["__seed"] = spec.seed. السكربت التجريبي بيستخدمه في np.random.default_rng(seed)، فتشغيلتين بنفس الـ seed بيدّوا أرقام متطابقة.

ده شرط للـ evaluator بتاع الدرس ٥٣: من غير determinism، أي «regression» ممكن يطلع بس تهيئة عشوائية مختلفة. ومع ثبات الـ seed تقدر تفرّق بين تغيير حقيقي وضوضاء.

السكربت التجريبي: بيقرا مسار ملف الـ config من argv، ويحاكي تدريب صغير (loss curve + perplexity نهائي + wall time). بيدعم sleep_s لإجبار timeout، وallocate_mb لإجبار الـ memory poller. هو مش بيدرّب حاجة حقيقية: الدرس عن الـ runner مش عن التجربة.

خطوة ٢: قراءة الـ RSS والـ Poller

def _rss_mb(pid):
    path = f"/proc/{pid}/status"
    if os.path.exists(path):                      # لينكس
        with open(path) as fh:
            for line in fh:
                if line.startswith("VmRSS:"):
                    return float(line.split()[1]) / 1024.0   # kB -> MB
        return 0.0
    return None                                   # مش مدعوم (الأصل بيجرّب ps كمان)

class _MemoryPoller(threading.Thread):
    def __init__(self, proc, cap_mb, interval_s=0.05):
        super().__init__(daemon=True)
        self._proc, self._cap, self._interval = proc, cap_mb, interval_s
        self._stop_event = threading.Event()
        self.peak_rss_mb = None
        self.killed_for_oom = False

    def stop(self):
        self._stop_event.set()

    def run(self):
        while not self._stop_event.is_set() and self._proc.poll() is None:
            rss = _rss_mb(self._proc.pid)
            if rss is None:                       # مفيش طريقة نقيس: اقفل الـ poller
                return
            self.peak_rss_mb = rss if self.peak_rss_mb is None else max(self.peak_rss_mb, rss)
            if rss > self._cap:                   # عدّى الـ cap: اقتله
                self.killed_for_oom = True
                self._proc.kill()
                return
            self._stop_event.wait(self._interval) # نام لحد النظرة الجاية

خطوة ٣: استخراج الـ metrics من الـ stdout

def _scan_intermediates(stdout, metric_keys):
    intermediates, final = [], {}
    required = set(metric_keys)
    for raw in stdout.splitlines():
        line = raw.strip()
        if not line.startswith("{"):
            continue
        try:
            parsed = json.loads(line)
        except json.JSONDecodeError:
            continue
        if not isinstance(parsed, dict):
            continue
        if required and not required.issubset(parsed.keys()):
            continue                              # مش covering line
        if final:
            intermediates.append(final)           # القديم يبقى intermediate
        final = parsed                            # الأحدث هو النهائي
    return final, intermediates

خطوة ٤: الـ Runner نفسه والـ terminal label

class ExperimentRunner:
    def __init__(self, python_path=None, poll_interval_s=0.05):
        self._python = python_path or sys.executable
        self._poll_interval = poll_interval_s

    def run(self, spec):
        with tempfile.TemporaryDirectory(prefix="exp_") as workdir:
            cfg_path = os.path.join(workdir, "config.json")
            cfg = dict(spec.config)
            cfg["__seed"] = spec.seed             # الـ seed بيدخل من الـ config
            with open(cfg_path, "w") as fh:
                json.dump(cfg, fh)
            return self._run_subprocess(spec, cfg_path)

    def _run_subprocess(self, spec, cfg_path):
        start = time.perf_counter()
        proc = subprocess.Popen([self._python, spec.script_path, cfg_path],
                                stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True)
        poller = _MemoryPoller(proc, spec.memory_cap_mb, self._poll_interval)
        poller.start()
        timed_out = False
        try:
            stdout, stderr = proc.communicate(timeout=spec.wall_timeout_s)
        except subprocess.TimeoutExpired:
            timed_out = True
            proc.kill()
            stdout, stderr = proc.communicate(timeout=2.0)
        finally:
            poller.stop(); poller.join(timeout=1.0)
        metrics, inter = _scan_intermediates(stdout, spec.metric_keys)
        terminal = self._terminal_label(proc.returncode, timed_out,
                                        poller.killed_for_oom, bool(metrics))
        return ExperimentResult(spec.spec_id, spec.hypothesis_id, proc.returncode, terminal,
                                time.perf_counter() - start, poller.peak_rss_mb,
                                metrics, inter, stdout, stderr)

    @staticmethod
    def _terminal_label(exit_code, timed_out, oomed, have_metrics):
        if oomed:     return "oom"                # الأولوية ١
        if timed_out: return "timeout"            # ٢
        if exit_code == 0 and have_metrics: return "ok"
        return "crash"                            # أي حاجة تانية

ملحوظة: الأصل بيتعامل كمان مع فشل Popen نفسه (OSError) وبيرجّع result بـ exit_code=-1 وterminal="crash". زوّد ده في نسختك.

خطوة ٥: الـ ablate والـ AblationRunner

def ablate(base, knob, values):
    specs = []
    for v in values:
        cfg = dict(base.config)
        cfg[knob] = v                              # مفتاح واحد بس بيتغير
        specs.append(ExperimentSpec(
            spec_id=f"{base.spec_id}_{knob}_{v}",
            hypothesis_id=base.hypothesis_id, script_path=base.script_path,
            config=cfg, seed=base.seed, wall_timeout_s=base.wall_timeout_s,
            memory_cap_mb=base.memory_cap_mb, metric_keys=list(base.metric_keys)))
    return specs

class AblationRunner:
    def __init__(self, runner):
        self._runner = runner
    def sweep(self, base, knob, values):
        values = list(values)
        rows = [(v, self._runner.run(s)) for v, s in zip(values, ablate(base, knob, values))]
        return rows

خطوة ٦: السكربت التجريبي (اللي بيتشغّل جوه الـ subprocess)

الأصل في code/experiments/sparsity_experiment.py وبيستخدم numpy. دي نسخة مختصرة توضّح العقد (قراءة config، طباعة JSON لكل step، وسطر نهائي):

import json, sys, numpy as np

cfg = json.load(open(sys.argv[1]))                # مسار الـ config جاي من argv
rng = np.random.default_rng(int(cfg.get("__seed", 0)))
k, steps = int(cfg.get("k", 8)), max(1, int(cfg.get("steps", 4)))
losses = []
for step in range(steps):
    loss = 5.0 * (0.9 ** step) - 0.05 * min(k, 32) / 32.0 + float(rng.normal(0, 0.02))
    losses.append(round(loss, 6))
    print(json.dumps({"step": step, "loss": losses[-1],
                      "perplexity": round(float(np.exp(losses[-1])), 6),
                      "final_loss": losses[-1]}), flush=True)   # intermediate
print(json.dumps({"perplexity": round(float(np.exp(losses[-1])), 6),
                  "final_loss": losses[-1], "steps_completed": steps,
                  "k": k, "seed": int(cfg.get("__seed", 0))}), flush=True)  # النهائي

وبعدين جرّب الـ demo بتاعك بنفس الـ config: {"k": 16, "steps": 4, "sleep_s": 0.0} وseed=7، وقارن الشكل (مش لازم الأرقام تطابق لو شغّلت نسخة مختصرة). الـ tests الأصلية في code/tests/test_runner.py (success / timeout / crash / ablation / determinism).

إضافة مني: اللي الدرس مقالهوش

إضافة مني: حاجات الدرس مقالهاش صراحة وتفرق في الشغل الحقيقي.

الحدس: الـ runner هو «الحد الفاصل بين الكلام والأرقام». أي إهمال في القياس (ذاكرة، وقت، seed) بيتحول في الآخر لحكم غلط في الـ evaluator. عشان كده الـ result مبيحذفش الفشل: بيسجّله بـ label واضح.
  • خطأ شائع ١: deadlock الـ pipes. الأصل بيستخدم communicate() اللي بيقرا stdout وstderr في نفس الوقت. لو استخدمت proc.wait() وبعدين قرأت الـ pipes، والسكربت طبع كمية كبيرة، الـ pipe بيتملي والبروسيس بيعلّق للأبد.
  • خطأ شائع ٢: تكتب الـ seed في السكربت. الـ seed لازم يجي من الـ spec، وإلا الـ ablation مبقاش قابل للمقارنة.
  • خطأ شائع ٣: تثق في الـ metrics بعد crash. حتى لو في JSON، الـ exit code الغير صفر معناه إن التجربة مخلصتش. الأصل بيعتبرها failure.
  • حدود الدرس: الـ poller بيقيس البروسيس الأب بس (الـ pid المباشر). لو السكربت فتح child processes، ذاكرتهم مش محسوبة. وده فرق بين «العقد» و«sandbox حقيقي» (cgroups).
  • في الـ LLMs والـ agents: أي agent بينفّذ كود (code interpreter، SWE-agent، eval harness) محتاج نفس الثلاثية: timeout + memory limit + terminal reason واضح. وده نفس الأساس اللي في الـ code-execution metrics (دروس قدّام).
