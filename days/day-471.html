  1. الـ download اتقطع عند 41%. إزاي تكمّله من غير ما تبدأ من الأول؟

01

المشكلة: ليه JSONL بيموت تحت الـ trainer؟

تدريب LLM حقيقي بيقرا tokens بمئات الآلاف من العينات في الثانية، من عشرات الـ workers. الـ JSONL على الديسك بيقع من أول cold-cache page fault، لأن:

  • الـ JSON parser بطيء.
  • حدود الـ documents مش «قابلة للعنونة»: عشان توصل لـ «العينة رقم 4,217,884» لازم تمسح الملف من الأول.
  • حتى Parquet (بيضغط كويس) مش مناسب، لأن الـ trainer مش عايز أعمدة. عايز stream مسطّح من الـ tokens مع وصول عشوائي بتكلفة O(1).
تشبيه: JSONL زي كتاب مفيهوش فهرس ولا أرقام صفحات: عشان تلاقي الجملة لازم تقلّب من الغلاف. HDF5 المقسوم لـ chunks زي كتاب مترقّم الصفحات ومقسوم لكراريس ثابتة الحجم: تقول «هات من الصفحة 3,200,000 لـ 3,208,192» وتفتح على طول.

HDF5 بيدّيك dataset integer-only، resizable، chunked. الـ trainer بيطلب tokens[3_200_000 : 3_208_192] وHDF5 بينسخ الـ slice من الـ page cache لـ NumPy array جديد. التكلفة: file handle واحد + chunk واحد في الـ cache لكل worker.

المشكلة الحقيقية في الـ write side: الـ resizable datasets سهل تستخدمها غلط.

02

Resizable HDF5 بالطريقة الصح: buffer ثم extend

الـ dataset بيتعمل بـ maxshape=(None,) (يعني «ممكن يكبر لأي طول») وchunks=(chunk_size,) (حجم ثابت). الكتابة بتمشي كده:

  1. بتجمّع الـ tokens في buffer في الذاكرة طوله chunk_size.
  2. لما الـ buffer يتملي بالظبط: resize للـ dataset بمقدار chunk_size بالظبط، وتكتب الـ buffer في المدى الجديد.
  3. في آخر الـ shard: الباقي (residual buffer) بيتكتب في مدى أخير جزئي.

كل كتابة contiguous ومتحاذية مع الـ chunk ما عدا الأخيرة. والأخيرة دي بالذات ممكن تسيب خانات فاضية، عشان كده الـ reader لازم يتقصّ عند token_count المسجّل في الـ attributes (نشرحها في القسم الجاي).

number_of_resizes = ceil(total_tokens / chunk_size) ← بدل total_tokens (واحد لكل token!)
تشبيه: بتنقل عفش بالعربية. تحمّل العربية للآخر (buffer ممتلي) وتروح رحلة، أحسن ما تعمل رحلة لكل كرسي. وماتستناش لحد ما كل الشقة تتحمّل في رحلة واحدة، لأن لو العربية اتعطلت في النص كل حاجة راحت.

معمل ١: كام resize هتعمل؟

غيّر عدد الـ tokens وحجم الـ chunk. شوف الفرق بين الكتابة token-by-token والكتابة بالـ buffer، وكام token هيفضل في الـ residual buffer آخر الـ shard.

لاحظ: لما الـ chunk كبير جدًا، عدد الـ resizes بيقل أكتر، بس الـ buffer بياخد ذاكرة أكتر وكمان الـ granularity بتاع الـ flush بيكبر. الـ trade-off موجود.
03

Sharded write، وshards.json، وtoken_count في الـ attributes

ملف HDF5 واحد = single point of failure. فالـ pipeline بيكتب shards بالتوازي: كل input shard (من درس 42) بيطلّع HDF5 output shard واحد (1:1). ده بيخلي الـ resume والـ recovery من الفشل الجزئي بسيطين.

ملف shards.json هو الـ index: لكل shard بيسجّل المسار (path)، عدد الـ tokens، عدد الـ documents، وsha256 على bytes الـ tokens. الـ trainer بيقراه مرة واحدة عند البداية، بيحسب منه الـ global offsets، وبيتحقق منه الـ corpus. ومش بيلمس الـ directory listing أبدًا.

ليه token_count attribute مش الـ shape؟ لأن آخر chunk ممكن يبقى نصف مليان (حجم الـ chunk مش بيقسم حدود الـ document). لو الـ reader مشي لآخر الـ dataset هيدخل على tokens أصفار (zero-padded) والموديل يتعلّم يتوقع صفر. فبنخزّن الرقم الحقيقي كـ attribute ونخلي الـ reader يقف عنده.

سيناريو: الـ shard فيه 10,000 token حقيقي وchunk=4096. الـ dataset هيبقى حجمه 10,000 (لأن آخر write كان حجمه الفعلي، في كود الدرس) لكن في تصميم تاني ممكن يتملي لـ 12,288. الـ attribute token_count=10000 هي الحقيقة في الحالتين.

معمل ٢: ماشي في الـ pipeline خطوة خطوة

دوس «التالي» وشوف كل مرحلة: JSONL، tokenize، buffer، resize، write، close، shards.json، وبعدين الـ window.

04

القراءة: chunked read وswmr

وقت التدريب، كل worker بيفتح نصيبه من ملفات HDF5 بـ swmr=True وبيطلب tokens[start:stop]. h5py مش بيعمل memory-map للملف: بيقرا chunks كاملة عن طريق الـ HDF5 chunk cache والـ OS page cache، وبعدين ينسخ الـ hyperslab المطلوب بس. الـ worker ما بيحمّلش الملف كله أبدًا: الـ slice بيتنسخ في الـ batch buffer، وبعدها في tensor الـ training الـ pinned-memory وقت الـ batch. الـ hot path فيه syscall واحد لكل انتقال chunk، والباقي RAM.

تنبيه على الاسم: الكلاس في الكود اسمه MmapTokenStore بس الدرس نفسه بيقول إن الاسم للراحة؛ هو بيقرا chunks مش mmap.

SWMR: Single-Writer-Multiple-Reader

عشان الـ readers يقروا بأمان والـ writer بيكتب: الـ writer يفتح الملف بـ libver="latest"، يعمل كل الـ datasets الأول، وبعدين يفعّل file.swmr_mode = True، وبعد كل resize يعمل dataset.flush(). الـ readers يفتحوا بـ swmr=True. لو نسيت libver="latest" أو فعّلت SWMR بعد تغييرات هيكلية، تجيلك أخطاء «file is locked».

انتبه (ممكن يلخبطك): كويز الدرس بيقول إن swmr=True بتتفتح على جنب الـ reader مش الـ writer. بس كود الـ writer في الدرس بيفعّل file.swmr_mode = True بعد إنشاء الـ dataset (ده الجزء الخاص بالـ writer من البروتوكول). الاتنين صح: الـ writer بيحتاج libver="latest" + تفعيل الـ mode، والـ readers بيفتحوا بـ swmr=True. الجملة اللي تحفظها: «الـ reader بيفتح swmr=True، والـ writer بيفتح latest ويفعّل الـ mode بعد ما يكمّل الهيكل».
05

الـ Sliding-window dataloader وقواعد الـ packing

الـ dataloader هو الوحيد اللي يعرف طول الـ training sequence. بيختار start index عشوائي في الـ global token stream، بيقرا window_size + 1 token، وبيرجّع:

input = tokens[:-1] target = tokens[1:] ← إزاحة بواحد (next-token prediction)

حدود الـ documents مش مفروضة: الـ window ممكن يعدّي على documentين، مع boundary_token_id صريح بينهم عشان الموديل يتعلّم يستخدم الفاصل. ده الـ packing القياسي. وده كمان اللي المبتدئ بينساه، فيطلع corpus فيه 8% boundary tokens و92% نص طبيعي (مثال الدرس).

تشبيه: فكّر في شريط فيلم طويل ملزوق فيه مشاهد كتير. بتقص منه شرائح بطول ثابت. الـ boundary token هو «علامة القطع» بين المشاهد، من غيرها الموديل هيفتكر إن الجملة الأولى في مشهد بتكمّل آخر جملة في اللي قبله.

معمل ٣: window، input، target

حرّك الـ window على stream صغير فيه boundary token (الرقم 0 بالأحمر). شوف الـ input والـ target كإزاحة بواحد.

لاحظ: الـ target دايمًا هو الـ input متزاح خانة. وآخر token في الـ window بيظهر في الـ target بس، وأول token في الـ input بيظهر في الـ input بس.

معمل ٤: الـ chunk ولا الـ window؟

الـ trainer بيقرا window_size + 1 token لكل عينة. المنحنى بيوريك متوسط عدد الـ chunks اللي كل عينة بتلمسها حسب نسبة حجم الـ chunk للـ window. الدرس بيقول: «اضبط الـ chunk على مضاعف للـ window، وإلا الـ throughput بينقص للنص لأن كل عينة بتلمس chunkين».

ملاحظة مني: الصيغة اللي في المعمل تقريب بسيط (بفرض start عشوائي موزع بانتظام)، هدفها تديك الإحساس بالاتجاه، مش رقم قياس حقيقي. القياس الحقيقي هو تمرين ٤ تحت.

Milestone 1: الـ Tokenizer (byte-level)

Vocabulary بسيط: 0 = boundary token، و1..256 = bytes (مزاحة بواحد عشان 0 محجوز). مش BPE حقيقي، بس كفاية نشوف القصة.

BOUNDARY_TOKEN_ID = 0

class Tokenizer:
    BYTE_OFFSET = 1            # نزيح كل byte بواحد عشان 0 يفضل للـ boundary
    def __init__(self):
        self.vocab_size = 257  # 256 byte + boundary

    def encode(self, text):
        if not text:
            return []
        return [self.BYTE_OFFSET + b for b in text.encode("utf-8")]

    def decode(self, ids):
        data = [int(i) - self.BYTE_OFFSET for i in ids if int(i) >= self.BYTE_OFFSET]
        return bytes(data).decode("utf-8", errors="replace")

Check: Tokenizer().decode(Tokenizer().encode("أهلا hi")) لازم يرجّع النص الأصلي. جرّب كمان نص عربي: الحروف العربية بتاخد أكتر من token لأن كل حرف 2 bytes في UTF-8.

Milestone 2: الـ HDF5ShardWriter (buffer ثم extend)

import hashlib, h5py, numpy as np

class HDF5ShardWriter:
    def __init__(self, path, chunk_size=4096):
        self.path, self.chunk_size = path, chunk_size
        self._buffer = []                 # الـ tokens اللي لسه ما اتكتبوش
        self._token_count = 0
        self._document_count = 0
        self._hasher = hashlib.sha256()   # هاش على bytes الـ tokens

    def __enter__(self):
        self._file = h5py.File(self.path, "w", libver="latest")
        self._dataset = self._file.create_dataset(
            "tokens", shape=(0,), maxshape=(None,),   # يكبر بلا حدود
            chunks=(self.chunk_size,), dtype=TOKEN_DTYPE)
        self._file.swmr_mode = True       # بعد ما الـ dataset اتعمل
        return self

    def add_document(self, token_ids):
        self._document_count += 1
        for t in token_ids:
            self._buffer.append(int(t))
            if len(self._buffer) >= self.chunk_size:
                self._flush_buffer(final=False)

    def _flush_buffer(self, final):
        size = len(self._buffer) if final else self.chunk_size
        chunk = np.asarray(self._buffer[:size], dtype=TOKEN_DTYPE)
        new_total = self._token_count + size
        self._dataset.resize((new_total,))                 # resize بالظبط بحجم الـ chunk
        self._dataset[self._token_count:new_total] = chunk # اكتب في المدى الجديد
        self._dataset.flush()                              # عشان الـ readers يشوفوا
        self._hasher.update(chunk.tobytes())
        self._token_count = new_total
        self._buffer = self._buffer[size:]

    def __exit__(self, *exc):
        if self._buffer:
            self._flush_buffer(final=True)                 # الباقي
        self._dataset.attrs["token_count"] = self._token_count
        self._dataset.attrs["document_count"] = self._document_count
        self._dataset.attrs["sha256"] = self._hasher.hexdigest()
        self._file.close()

(TOKEN_DTYPE معرّف في أول الملف الأصلي. افتح الأصل وشوف نوعه.)

Milestone 3: الـ pipeline وshards.json

الـ ShardedTokenizationPipeline بياخد documents لكل shard، بيرميها على writer، وبيكتب الـ index. الفكرة (مبسطة):

def write_shard(self, shard_id, documents):
    path = self.output_dir / f"{shard_id}.h5"
    with HDF5ShardWriter(path, self.chunk_size) as w:
        for doc in documents:
            w.add_document(self.tokenizer.encode(doc))
            w.add_boundary()           # فاصل بعد كل document
    return w.result(shard_id)          # path, token_count, document_count, sha256 ...

Milestone 5: الـ SlidingWindowDataloader

class SlidingWindowDataloader:
    def __init__(self, store, window_size=128, batch_size=4, seed=0):
        self.store, self.window_size, self.batch_size = store, window_size, batch_size
        self._random = random.Random(seed)             # seed ثابت = نفس الـ batches
        self._max_start = store.total_tokens - window_size - 1

    def _sample_window(self):
        start = self._random.randint(0, self._max_start)
        chunk = self.store.get_slice(start, start + self.window_size + 1)
        return chunk[:-1], chunk[1:]                   # input و target (إزاحة بواحد)

    def __iter__(self):
        while True:
            inputs  = np.empty((self.batch_size, self.window_size), dtype=TOKEN_DTYPE)
            targets = np.empty((self.batch_size, self.window_size), dtype=TOKEN_DTYPE)
            for row in range(self.batch_size):
                inputs[row], targets[row] = self._sample_window()
            yield inputs, targets

(القيمة الافتراضية للـ window في الأصل اسمها DEFAULT_WINDOW_SIZE. افتح الأصل وشوفها.) Check: كل batch شكله (batch_size, window_size) للـ input والـ target، وtargets[:, :-1] == inputs[:, 1:] دايمًا.

    تلميحاقرا f["tokens"][:token_count] (متنساش القص عند token_count)، واعمل hashlib.sha256(arr.tobytes()).hexdigest(). لازم يطابق اللي اتسجّل. جرّب تبوّظ byte في ملف وتتأكد إن الـ validate بيفشل.
  4. قارن throughput الـ dataloader لما الـ chunk = الـ window ونصه وضعفه. اكتب تقرير عن تأثير الـ page cache.
    تلميحثبّت الـ seed والـ batch size وعدد الـ batches. شغّل كل إعداد مرتين: الأولى بتسخّن الـ cache والتانية هي اللي بتقيسها. اعمل نفس القياس بعد تفريغ الـ cache لو تقدر. توقّع (من الدرس) إن الـ chunk الأصغر من الـ window هيبقى الأبطأ.
  5. أضف flag --max-document-tokens بيقصّ الـ documents الطويلة جدًا وقت الكتابة. دافع عن الـ trade-off ضد القرار وقت القراءة.
    تلميحالقص وقت الكتابة بيوفّر مساحة وبيبسّط الـ reader، بس بيرمي داتا للأبد (ما تقدرش تغيّر رأيك من غير ما تعيد الـ tokenization). القرار وقت القراءة مرن، بس بيدفع تكلفة قراءة tokens مش هتستخدمها.
  6. تمرين مني · مشروع صغير كامل: اعمل script build_corpus.py بياخد مجلد JSONL، يشغّل الـ pipeline، يكتب shards.json، يعمل --validate، ويطبع جدول: shard، tokens، documents، نسبة الـ boundary tokens من الإجمالي.
    الإجابة المقترحةنسبة الـ boundary = عدد الـ documents ÷ عدد الـ tokens (لأن فيه boundary واحد لكل document). لو النسبة عالية (مثلًا documents قصيرة جدًا) يبقى تدريبك بيصرف قدر ملحوظ من الـ tokens على الفواصل. اطبع تحذير لو عدّت نسبة اخترتها (مثلًا 5%).
09

إضافة مني: أخطاء، وفين ده بيظهر في الـ LLMs

  • تنسى flush() بعد كل resize: الـ readers (SWMR) ممكن يشوفوا حجم الـ dataset من غير البيانات اللي اتكتبت. الدرس بيعملها بعد كل write.
  • تحسب الطول من len(dataset) بدل token_count: لو ملفك فيه padding في آخر chunk، الموديل هيتعلّم أصفار. دايمًا اقصّ عند الـ attribute.
  • الـ boundary token في الـ loss: قرّر صراحة: الموديل يتعلّم يتوقعه (يتعلم الفاصل) ولا الـ loss يعمله mask؟ المهم تقرّر بوعي.
  • الـ seed بيتعمل لكل worker: لو كل الـ workers بنفس الـ seed هيطلعوا نفس الـ windows. في التدريب الحقيقي الـ seed لازم يتوزع حسب الـ worker/rank.
  • الـ dtype بيفرق في الحجم: لو الـ vocab أقل من 65,536 تقدر تخزّن uint16 بدل int32 وتوفّر نص الحجم. وفي مشروعك لازم الـ dtype يكفي أكبر token id.
  • فين بيظهر: أي pretraining حقيقي (نصوص مرصوصة packed في stream طويل بيتقطع لـ sequences بطول الـ context) بيعتمد على نفس الفكرة، وعشان كده كل الـ loaders الكبيرة بتكتب tokens في binary shards ثابتة بدل JSON.
