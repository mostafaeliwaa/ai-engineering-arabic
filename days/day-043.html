المشكلة: موديل churn «ممتاز» على الورق

فريق عامل موديل churn. كل label بيقول: هل اليوزر ده مشتراش أي حاجة في الـ ٣٠ يوم اللي بعد يوم الـ label؟ عملوا join بين الـ labels وجدول الـ features على user_id بس، ودرّبوا rule بسيطة على days_since_last_purchase. الـ accuracy offline طلعت 0.948.

على الترافيك الحقيقي، الموديل طلع أسوأ من نسخة قديمة أبسط منه. ليه؟ عيبين:

  1. سفر عبر الزمن: جدول الـ features كان فيه أحدث قيمة لكل يوزر، من أسابيع بعد أيام الـ labels. يوزر آخر شراء ليه يوم 115 كان ظاهر في snapshot يوم 175 إنه بقاله 60 يوم مشتراش. يعني الـ feature كان شايل الإجابة نفسها.
  2. كود تاني للـ serving: فريق تاني كتب الـ features من الأول في service تانية. الـ window بتاعتهم (٣٠ يوم) فيها يوم زيادة، والـ default لليوزر الجديد عندهم -1 بدل 365.
السبب واحد: الـ training والـ serving حسبوا «نفس الـ feature» بطريقتين مختلفتين. الحل: تعريف واحد، الاتنين بيقروا منه. ده بالظبط اللي الـ feature store بيعمله.

02

الـ Point-in-Time Join: صورة الماضي زي ما كانت

كل صف training بيجمع label مع قيم الـ features اللي كانت موجودة وقت الـ label. الخطوات لكل label:

  1. هات صفوف الـ features لنفس الـ entity.
  2. خلّي بس الصفوف اللي الـ event timestamp بتاعها ≤ وقت الـ label.
  3. خد أحدث واحد فيهم.
  4. لو (وقت الـ label − وقت الصف) > TTL، ارميه واستخدم الـ default.

تشبيه: محقق بيسأل «كنت فين يوم الحادثة؟» لازم يبص على صور الكاميرا لحد اللحظة دي بس. لو بص على صور بعدها، هيعرف النتيجة قبل ما يحقق.

جرب بإيدك: اسحب علامة الـ label (الخط الأزرق) على الـ timeline، وغيّر الـ TTL. الـ PIT join بيختار آخر صف قبله، والـ naive join (على user_id بس) بيختار دايمًا آخر صف خالص، حتى لو من المستقبل.

المثال من الدرس: label يوم 16، صفوف أسبوعية. الـ PIT بياخد يوم 14 (purchases_30d=3). الـ naive بياخد يوم 28 (0) لأن اليوزر بطّل يشتري، وده بالظبط الحدث اللي الـ label بيقيسه. الـ naive join نسخ الإجابة جوه المدخل.

ده نفس المنطق اللي خلانا في درس الـ time series نقسم الداتا بالزمن. الـ point-in-time join بيطبق القاعدة دي على كل صف بدل نقطة تقسيم واحدة.

أسباب الـ Training-Serving Skew الأربعة

دليل Google «Rules of Machine Learning» بيعرّف الـ training-serving skew إنه فرق بين أداء الموديل في التدريب وأداؤه في الـ serving، وبيذكر ٣ أسباب: معالجة مختلفة للداتا في الـ pipelines، داتا اتغيرت بين التدريب والـ serving، و feedback loop. في الـ feature pipelines بالذات، أربع أسباب بتتكرر:

السبباللي بيحصلمن الـ demo
Two code pathsالـ training والـ serving بيحسبوا بكود مختلفwindow الـ serving فيها يوم now - 30، والـ training لأ
Stale featuresعمر القيمة في الـ serving مختلف عن اللي اتدرب عليهالـ training بيقرا snapshots أسبوعية، و service جديدة بتحسب قيم fresh
Different defaultsكل path بيملا الـ missing بشكلالـ training: 365 لـ «لسه مشتراش»، الـ serving: -1
Time travelالـ training قرا قيمة من بعد وقت الـ labelالـ naive join قرا أحدث snapshot لكل label

Rule #32 في نفس الدليل: استخدم نفس الكود بين الـ training pipeline والـ serving pipeline كل ما تقدر. الـ feature store بيطبقها بتعريف واحد الاتنين بينادوه.

معمل: شوف الـ skew بعينك

دي مشتريات يوزر واحد (النقط البرتقاني). حرّك «دلوقتي» (يوم الـ request) وقارن ٣ طرق لحساب نفس الـ features:

  • • Training/Online store: آخر snapshot أسبوعي ≤ دلوقتي (ده اللي الموديل اتعلم عليه).
  • • Fresh compute: نفس التعريف بس محسوب دلوقتي بالظبط.
  • • Legacy path: كود الفريق التاني: window فيها يوم زيادة و default = -1.

جرب «يوزر جديد» وشوف days_since_last_purchase: 365 قصاد -1. وحط «دلوقتي» على يوم يكون فيه شراء بالظبط عند حافة الـ window (now − 30) وشوف الـ count بيختلف.

ملاحظة مهمة: الـ fresh مش «أصح» هنا. الموديل اتعلم على قيم عمرها لحد ٦ أيام، فلو غذيته بقيم fresh انت بتديله توزيع ماشافهوش. الـ freshness جزء من تعريف الـ feature.

إزاي تكتشف الـ skew

Rule #29: سجّل (log) الـ features وقت الـ serving واستخدمها في التدريب. حتى sample صغير مسجل بيخليك تقارن: كل قيمة مسجلة مع اللي الـ training path بيطلّعه لنفس الـ entity ونفس الوقت. لكل feature طلّع نسبة الاختلاف (mismatch rate) ومتوسط الفرق المطلق (mean |diff|).

عشان تعرف السبب، قارن ٣ أزواج:

  1. Online store read مقابل training join: بيختبر السيستم كله، ولازم يطلع skew = صفر.
  2. Fresh compute مقابل training join: بيعزل الـ staleness.
  3. Second code path مقابل fresh compute: بيعزل اختلاف الكود (windows و defaults).

زي الدكتور اللي بيعزل السبب: يغير متغير واحد في كل مرة.

الـ Registry والـ Backfill

الـ Feature Registry: كتالوج التعريفات

كل entry فيه: name، entity، source، transformation، window، default، TTL، owner، version، description. وقاعدتين بيحموه:

  • • الـ path الاتنين بيقروا التعريف من الـ registry. ولا service عندها نسخة خاصة من الـ transformation.
  • • أي تغيير في التعريف = version جديدة. القديمة بتفضل موجودة، عشان الموديلات القديمة تفضل تاخد الـ feature اللي اتدربت عليه.

تشبيه: وصفة المطعم المكتوبة في كتاب واحد. لو الشيف غيّر كمية الملح، يكتب «وصفة v2» ومايمسحش v1، عشان الفرع اللي لسه شغال على v1 مايتفاجئش.

الموديل بيثبّت التعريف بمرجع زي spend_30d@1. اسم من غير @ بيقرا أحدث version. ولو كتبت @ من غير رقم الكود بيرمي ValueError، عشان typo مايقراش أحدث version من غير ما تاخد بالك.

الـ Backfill: تاريخ لـ feature لسه مولود

feature جديد ملوش تاريخ، بس التدريب محتاج قيمته عند كل label قديم. الـ backfill بيشغّل التعريف عند كل تاريخ قديم ويكتب صف لكل (entity, date). كل run بيقرا بس الـ events اللي timestamp بتاعها ≤ التاريخ ده.

فخ خفي: backfill اتعمل النهاردة بيكتب صفوف بـ event timestamps قديمة، بس ممكن يكون قرا داتا وصلت متأخر أو اتصححت بعدين. عشان كده الـ strict PIT join بيشيك كمان إن الـ created timestamp ≤ وقت الـ label. الـ event timestamp بيقول القيمة كانت صح امتى، والـ created timestamp بيقول السيستم عرفها امتى.

معمل: تكلفة الـ backfill

التكلفة بتكبر بـ (عدد الـ entities × عدد التواريخ). الـ demo: 299 يوزر × 25 snapshot يوم = 7475 صف. حرّك وشوف إزاي الرقم بيتفجر لما تروح لملايين اليوزرز أو snapshots يومية بدل أسبوعية.

خطوة ١: الـ FeatureDefinition (التحويل كـ data)

from __future__ import annotations
import bisect, random
from collections import defaultdict
from dataclasses import dataclass

@dataclass(frozen=True)
class Event:
    entity: str
    day: int
    amount: float

@dataclass(frozen=True)
class FeatureDefinition:
    name: str
    entity: str
    aggregate: str               # count / sum / days_since_last
    window_days: int | None      # None = كل التاريخ
    default: float
    version: int = 1
    owner: str = "growth-team"
    description: str = ""

    def compute(self, events: list[Event], as_of: int) -> float:
        visible = [e for e in events if e.day <= as_of]          # ممنوع المستقبل
        if self.window_days is not None:
            visible = [e for e in visible if e.day > as_of - self.window_days]  # الحافة الشمال مستبعدة
        if self.aggregate == "count":
            return float(len(visible))
        if self.aggregate == "sum":
            return round(sum(e.amount for e in visible), 2)
        if self.aggregate == "days_since_last":
            return float(as_of - max(e.day for e in visible)) if visible else self.default
        raise ValueError(f"unknown aggregate {self.aggregate!r}")

خطوة ٢: الـ Registry بالـ versions

class FeatureRegistry:
    def __init__(self) -> None:
        self._definitions: dict[tuple[str, int], FeatureDefinition] = {}

    def register(self, definition: FeatureDefinition) -> None:
        key = (definition.name, definition.version)
        existing = self._definitions.get(key)
        if existing is not None and existing != definition:   # نفس الاسم والـ version بتعريف مختلف = ممنوع
            raise ValueError(f"{definition.name} v{definition.version} already exists: bump the version")
        self._definitions[key] = definition

    def get(self, name: str, version: int | None = None) -> FeatureDefinition:
        versions = [v for (n, v) in self._definitions if n == name]
        if not versions:
            raise KeyError(name)
        return self._definitions[(name, version if version is not None else max(versions))]

    def resolve(self, ref: str) -> FeatureDefinition:          # "spend_30d@1" أو "spend_30d"
        if "@" not in ref:
            return self.get(ref)
        name, _, version = ref.partition("@")
        if not version.isdigit():
            raise ValueError(f"bad feature reference {ref!r}: use name@version, such as spend_30d@1")
        return self.get(name, int(version))

    def names(self) -> list[str]:
        return sorted({n for (n, _) in self._definitions})

    def compute(self, names, events, as_of):
        return {name: self.resolve(name).compute(events, as_of) for name in names}

    def fill_defaults(self, names, values):                     # نفس الـ default للـ path الاتنين
        values = values or {}
        return {name: values.get(name, self.resolve(name).default) for name in names}

def group_events(events):
    grouped = defaultdict(list)
    for event in events:
        grouped[event.entity].append(event)
    return grouped

def backfill(registry, names, events, days):
    rows = []
    for entity, entity_events in sorted(group_events(events).items()):
        for day in days:                                  # صف لكل (entity, day)
            rows.append(FeatureRow(entity, day, registry.compute(names, entity_events, day)))
    return rows

خطوة ٤: الـ point-in-time join (والـ naive للمقارنة)

def point_in_time_join(labels, rows, ttl_days=None):
    by_entity = defaultdict(list)
    for row in rows:
        by_entity[row.entity].append(row)
    days_index = {}
    for entity, entity_rows in by_entity.items():
        entity_rows.sort(key=lambda r: r.day)            # رتّب مرة واحدة
        days_index[entity] = [r.day for r in entity_rows]
    joined = []
    for label in labels:
        days = days_index.get(label.entity, [])
        pos = bisect.bisect_right(days, label.day) - 1  # آخر صف ≤ يوم الـ label
        match = by_entity[label.entity][pos] if pos >= 0 else None
        if match is not None and ttl_days is not None and label.day - match.day > ttl_days:
            match = None                                 # قديم أوي → default
        joined.append(JoinedRow(label.entity, label.day, label.label,
                                match.day if match else None, match.values if match else None))
    return joined

def naive_latest_join(labels, rows):                     # الغلط: join على الـ entity بس
    latest = {}
    for row in rows:
        if row.entity not in latest or row.day > latest[row.entity].day:
            latest[row.entity] = row
    return [JoinedRow(l.entity, l.day, l.label,
                      latest[l.entity].day if l.entity in latest else None,
                      latest[l.entity].values if l.entity in latest else None) for l in labels]

خطوة ٥: الـ online store بـ TTL والـ materialization

class OnlineStore:
    def __init__(self, ttl_days: int):
        self.ttl_days = ttl_days
        self._latest: dict[str, FeatureRow] = {}         # صف واحد لكل entity

    def write(self, row):
        current = self._latest.get(row.entity)
        if current is None or row.day >= current.day:    # القديم مايكتبش فوق الجديد
            self._latest[row.entity] = row

    def read(self, entity, now):
        row = self._latest.get(entity)
        if row is None or row.day > now or now - row.day > self.ttl_days:
            return None                                  # منتهي → الـ caller يحط defaults
        return dict(row.values)

    def age(self, entity, now):
        row = self._latest.get(entity)
        return None if row is None else now - row.day

def materialize(rows, store, up_to_day):
    written = 0
    for row in rows:
        if row.day <= up_to_day:                         # عمره ما يكتب صف من المستقبل
            store.write(row); written += 1
    return written

def training_features(registry, names, joined):
    return [registry.fill_defaults(names, row.values) for row in joined]

def serving_features(registry, names, store, entity, now):
    return registry.fill_defaults(names, store.read(entity, now))

خطوة ٦: الـ legacy path (الغلط عن قصد) والـ skew check

def legacy_serving_features(events, now):
    recent = [e for e in events if now - 30 <= e.day <= now]   # يوم زيادة: <= بدل <
    past = [e.day for e in events if e.day <= now]
    return {
        "days_since_last_purchase": float(now - max(past)) if past else -1.0,  # default غلط
        "purchases_30d": float(len(recent)),
        "spend_30d": round(sum(e.amount for e in recent), 2),
    }

@dataclass(frozen=True)
class SkewReport:
    feature: str
    compared: int
    mismatch_rate: float
    mean_abs_diff: float
    flagged: bool

def detect_skew(training, serving, features, tolerance=1e-6, max_mismatch_rate=0.01):
    if set(training) != set(serving):                   # request ناقص ممكن يخبي skew
        raise ValueError(f"{len(set(training) ^ set(serving))} keys are in only one view: log and compare the same requests")
    if not training:
        raise ValueError("no requests to compare")
    keys = sorted(training)
    reports = []
    for feature in features:
        diffs = [abs(training[k][feature] - serving[k][feature]) for k in keys]
        mismatches = sum(1 for d in diffs if d > tolerance)
        rate = mismatches / len(keys)
        reports.append(SkewReport(feature, len(keys), rate, sum(diffs) / len(keys), rate > max_mismatch_rate))
    return reports

باقي الملف (build_registry و make_events و make_labels و fit_idle_rule و log_serving_requests و main) بيعمل الداتا الصناعية (300 يوزر، 180 يوم، نص اليوزرز بيبطلوا يشتروا في يوم عشوائي) ويشغّل التجارب. اقراه من الأصل واكتبه، خصوصًا log_serving_requests اللي بيعمل materialize لحد يوم كل request وبعدين يقرا من الـ online store.

user = Entity(name="user", join_keys=["user_id"])

    timestamp_field="event_timestamp",
    created_timestamp_column="created",
)

    name="user_activity", entities=[user], ttl=timedelta(days=10),
    schema=[Field(name="purchases_30d", dtype=Int64),
            Field(name="spend_30d", dtype=Float32),
            Field(name="days_since_last_purchase", dtype=Int64)],
    source=user_activity_source,
)

store = FeatureStore(repo_path=".")
training_df = store.get_historical_features(            # training: PIT join
    entity_df=labels_df,                                  # user_id + event_timestamp + label

online = store.get_online_features(                       # serving: نفس الـ view

    entity_rows=[{"user_id": 42}],

توثيق Feast بيقول إن الـ TTL محسوب بالنسبة لكل timestamp في الـ entity dataframe، مش وقت الـ query، وده نفس الـ TTL check في point_in_time_join. ومش كل offline store بيدعم filter_by_created_timestamp؛ اللي مش بيدعمه بيرمي error بدل ما يتجاهله. Tecton و Hopsworks والـ feature stores في الـ cloud ML platforms الكبيرة بيستخدموا نفس التقسيم offline/online. وللـ skew check، TensorFlow Data Validation يقدر يقارن training data بالـ serving data.

التمارين

  1. Snapshot يومي: غيّر الـ interval من 7 لـ 1 (SNAPSHOT_DAYS = list(range(1, 176))). شغّل مقارنة الـ staleness تاني واشرح النتيجة.
    تلميحالـ snapshot بقى عمره دايمًا صفر أيام وقت الـ request، فالـ fresh compute والـ training join هيقربوا جدًا لبعض (الـ mismatch المفروض يقرب من صفر). الـ staleness كانت جاية من إن الـ snapshot عمره لحد ٦ أيام. التمن: rows أكتر بـ ٧ مرات تقريبًا في الـ backfill (جربها في معمل ٠٣).
  2. TTL = 3 أيام: عدّ صفوف الـ training اللي فقدت الـ features وخدت defaults.
    تلميحبعد pit = point_in_time_join(train_labels, offline, 3) عدّ sum(1 for r in pit if r.values is None). الـ labels أيام 100 و 120 و 140؛ شوف إيه أقرب snapshot قبل كل يوم (98، 119، 140) وعمره كام. اللي عمره أكبر من 3 هيقع.
  3. Created day: زوّد created_day في FeatureRow، وخلّي الـ join يتجاهل الصفوف المكتوبة بعد يوم الـ label.
    تلميحقبل الـ bisect، فلتر صفوف الـ entity لـ r.created_day <= label.day (أو اعمل index منفصل). اختبرها بصف event_day=14 بس created_day=30 وlabel يوم 20: لازم مايتاخدش.
  4. Version 2: سجّل spend_7d كـ version 2 من spend_30d. اعمله backfill واطبع الـ version الاتنين من الـ registry.
    تلميحFeatureDefinition("spend_30d", "user", "sum", 7, 0.0, version=2, description="spend in the last 7 days"). بعدين backfill(registry, ["spend_30d@1", "spend_30d@2"], events, SNAPSHOT_DAYS). لاحظ إن الاسم بقى مضلل؛ في الحقيقة غالبًا تسميه اسم جديد، والتمرين ده بيوريك ميكانيزم الـ versions.
  5. صلّح الـ legacy: عدّل legacy_serving_features لحد ما الـ skew check التالت يعدّي. اكتب كل تغيير.
    الإجابة(١) الـ window: now - 30 < e.day <= now بدل <= على الشمال. (٢) الـ default: 365.0 بدل -1.0. والأحسن من الاتنين: امسح الدالة دي ونادي registry.compute(FEATURES, events, now)، يعني Rule #32.
  6. إضافة مني · features لـ RAG / LLM app: عندك chatbot لخدمة العملاء بيحط في الـ prompt «خطة اليوزر» و«عدد التذاكر المفتوحة». اكتب FeatureDefinition لـ open_tickets_7d وابني eval set من محادثات قديمة بالـ point-in-time join (القيمة وقت المحادثة، مش النهاردة). بعدين اعمل log لقيم الـ prompt الحقيقية لـ 50 request وشغّل detect_skew عليها مقابل الـ training path.
    تلميحنفس الكود بالظبط: الـ entity = user_id، الـ events = فتح/قفل التذاكر، والـ label مش لازم (حط 0). المهم إن الـ eval بتاعك يشوف نفس اللي الـ LLM كان هيشوفه وقتها، وإلا الـ eval هيبان أحسن من الحقيقة.

إضافة مني: اللي الدرس ماقالوش صريح

الـ intuition في جملة

الـ feature مش «رقم»، هو رقم + لحظة + طريقة حساب. لو أي واحد من التلاتة اختلف بين التدريب والـ serving، الموديل بيشوف مدخل ماتعلمش عليه.

أخطاء شائعة

  • • الـ «accuracy عالية أوي» مش خبر حلو: لو الـ offline أحسن بكتير من المتوقع، أول حاجة تشك فيها هي leakage زمني.
  • • الـ timezones والـ off-by-one: الفرق بين < و<= على حافة الـ window هو اللي عمل 12.5% mismatch في الـ demo.
  • • الـ default كـ «قيمة عادية»: -1 لـ «أيام من آخر شراء» معناها للموديل «اشترى من شوية»، عكس المقصود تمامًا.
  • • «هحسبها fresh أحسن»: لو الموديل اتدرب على snapshots، الـ fresh بيعمل skew. يا تدرّب على نفس الـ freshness، يا تخلّي الاتنين من نفس المصدر.
  • • مقارنة requests مختلفة: الـ detect_skew بيرمي error لو المفاتيح مختلفة عشان مقارنة ناقصة ممكن تخبي المشكلة.

فين ده في الـ LLMs والـ Agents

  • • Evals بـ RAG: لو بتقيّم agent على أسئلة قديمة بس الـ retriever بيدور في الـ documents بتاعة النهاردة، ده time travel: الـ agent ممكن يلاقي الإجابة في مستند اتكتب بعد السؤال.
  • • الـ prompt features: أي context بتحطه في الـ prompt من DB (بيانات اليوزر، history) هو feature. لو الـ eval بيبنيه بكود والـ production بكود تاني، ده نفس الـ two code paths.
  • • Fine-tuning من logs: Rule #29 (سجّل اللي اتبعت فعلًا) بالظبط هو اللي بيخليك تعمل fine-tune على الـ prompts الحقيقية مش نسخة متخيلة منها.
