المشكلة والميزانيات التلاتة

شحن نظام رؤية يعني تحشر نفس التوقعات في ميزانية أصغر بـ 100 مرة. التلات مفاتيح اللي بتعمل أغلب الشغل: اختيار الموديل (معمارية أصغر بنفس الوصفة)، الـ quantisation (INT8 بدل FP32)، والـ runtime (ONNX Runtime، TensorRT، Core ML، TFLite). الفرق بين demo شغال على workstation ومنتج على كاميرا بـ 30 دولار هو إنك تظبطهم صح.

والدرس بيبدأ بالقياس لأن اللي متقدرش تقيسه متقدرش تحسّنه.

الميزانيةإيه المقصودفخ شائع
Latencyp50 وp95 وp99 (مش المتوسط بس)المتوسط بيخبّي الـ tail اللي بيكسر الأنظمة الـ real-time

قرار الـ edge بيتاخد من جدول (model, latency, memory, accuracy)، وكل خانة بتتقاس على الجهاز المستهدف مش الـ workstation.

انضباط القياس: تلات قواعد

  1. Warm up: 5–10 forward تجريبية قبل القياس. الـ cache البارد والـ JIT بيدّوا أرقام أول مرة مش تمثيلية.
  2. Synchronise مع الـ GPU: torch.cuda.synchronize() قبل وبعد المنطقة المقاسة. من غيرها بتقيس إطلاق الـ kernel مش تنفيذه.
  3. ثبّت حجم الدخل على دقة الإنتاج: latency على 224×224 غير 512×512.

معمل ١: ليه المتوسط بيكدّب؟

الأعمدة توزيع latency محاكي (أغلب الطلبات سريعة وقليل منها بطيء جدًا). زوّد «احتمال الـ spike» وشوف إزاي p99 بيطير بينما p50 والمتوسط تقريبًا ثابتين.

لاحظ: لو الـ SLA بتاعك 33ms (30fps) وp99 = 80ms، فكل مئة فريم هيفوتك واحد. وده مبيظهرش في المتوسط.

FLOPs كـ proxy

الـ FLOPs رقم رخيص ومستقل عن الجهاز، مفيد لمقارنة المعماريات، لكنه مضلل كزمن فعلي. موديل بـ 10% FLOPs زيادة ممكن يبقى أسرع مرتين لأنه بيستخدم عمليات مناسبة للهاردوير (الـ depthwise convs بتتcompile كويس، والـ 7×7 الكبيرة لأ). والعكس: depthwise قليلة الـ FLOPs لكنها memory-bound على الـ GPU. القاعدة: FLOPs لاختيار المعمارية، وlatency على الجهاز لقرار النشر.

02

Quantisation: من FP32 لـ INT8

استبدل أوزان وactivations الـ FP32 بـ INT8. حجم الموديل بينزل 4×، وعرض النطاق للذاكرة 4×، والحسبة 2–4× على الهاردوير اللي فيه kernels INT8 (كل SoC موبايل حديث وكل NVIDIA GPU بـ Tensor Cores). الخسارة في الدقة عادةً 0.1–1 نقطة مع post-training static.

تشبيه: بدل ما تكتب كل سعر بـ 6 أرقام عشرية، بتقرّبه لأقرب جنيه. الفاتورة بتبقى أخف بكتير، والفرق في الإجمالي صغير جدًا طالما التقريب منظم ومظبوط على نطاق الأسعار الفعلي (ده الـ calibration).
النوعبيعمل إيهإمتى
Dynamicالأوزان INT8، والـ activations بتتحسب بـ FPسهل، تسريع صغير
Static (PTQ)الأوزان + نطاقات الـ activations بتتعاير (calibration) على set صغيرأسرع بكتير من dynamic. الاختيار الأول للرؤية: 95% من الفايدة بـ 5% من المجهود
QATمحاكاة الـ quantisation وقت التدريب فالموديل يتعلم يتعايش معاهأحسن دقة، محتاج labelled data. استخدمه لما خسارة PTQ مش مقبولة

معمل ٢: شوف الـ quantisation بعينك

المنحنى الأزرق وزن/activation متصل، والمنحنى الثاني بعد ما قرّبناه لـ 2^bits مستوى. قلّل الـ bits وشوف الدرجات بتكبر. جرّب 8 وبعدين 4 وبعدين 2.

لاحظ: الـ INT8 (256 مستوى) تقريبًا مش بيبان على المنحنى. ده بالظبط ليه الخسارة صغيرة.

Pruning و Distillation

  • Pruning: شيل الأوزان الضعيفة (حسب الحجم magnitude) أو قنوات كاملة (structured). بيشتغل كويس على الموديلات الكبيرة جدًا، وأقل فايدة على المعماريات المضغوطة أصلًا.
  • Distillation: درّب student صغير يقلّد logits الـ teacher الكبير. بيرجّع معظم الدقة اللي ضاعت مع التصغير. معيار في موديلات الـ edge الإنتاجية.

عمليًا: صدّر PyTorch ← ONNX ← اختار الـ runtime للجهاز. ONNX هو «لغة التفاهم».

التلات مسارات الإنتاجية

  • Web / serverless: PyTorch ← ONNX ← ONNX Runtime (CPU أو CUDA). الأسهل وكفاية لمعظم الحالات.
  • NVIDIA edge (Jetson، GPU server): PyTorch ← ONNX ← TensorRT. أحسن latency وأكبر مجهود هندسي.
  • Mobile: PyTorch ← ONNX ← Core ML (iOS) أو TFLite (Android). اعمل quantise قبل التصدير.

للقياس: torch-tb-profiler وnvprof/nsys وInstruments على macOS بيدّوك تفصيل طبقة طبقة؛ وbenchmark_app (OpenVINO) وtrtexec (TensorRT) أرقام CLI مستقلة.

الخطوة ١: قياس الـ latency صح.

import time
import torch

def measure_latency(model, input_shape, device="cpu", warmup=10, iters=50):
    model = model.to(device).eval()
    x = torch.randn(input_shape, device=device)
    with torch.no_grad():
        for _ in range(warmup):                 # warm-up: نسخّن الـ cache والـ JIT
            model(x)
        if device == "cuda":
            torch.cuda.synchronize()
        times = []
        for _ in range(iters):
            if device == "cuda":
                torch.cuda.synchronize()        # نتأكد إن اللي قبل خلص
            t0 = time.perf_counter()
            model(x)
            if device == "cuda":
                torch.cuda.synchronize()        # نستنى الـ kernel يخلص فعلًا
            times.append((time.perf_counter() - t0) * 1000)   # ms
    times.sort()
    return {
        "p50_ms": times[len(times) // 2],
        "p95_ms": times[int(len(times) * 0.95)],
        "p99_ms": times[int(len(times) * 0.99)],
        "mean_ms": sum(times) / len(times),
    }

الخطوة ٢: عدّ البارامترات والـ FLOPs.

def parameter_count(model):
    return sum(p.numel() for p in model.parameters())

def flops_estimate(model, input_shape):
    total = 0
    def conv_hook(m, inp, out):                         # hook بيتنادى بعد كل conv
        nonlocal total
        c_out, c_in, kh, kw = m.weight.shape
        h, w = out.shape[-2:]
        total += 2 * c_in * c_out * kh * kw * h * w     # 2 لأن multiply + add
    def linear_hook(m, inp, out):
        nonlocal total
        total += 2 * m.in_features * m.out_features
    hooks = []
    for m in model.modules():
        if isinstance(m, torch.nn.Conv2d):
            hooks.append(m.register_forward_hook(conv_hook))
        elif isinstance(m, torch.nn.Linear):
            hooks.append(m.register_forward_hook(linear_hook))
    model.eval()
    with torch.no_grad():
        model(torch.randn(input_shape))
    for h in hooks:
        h.remove()
    return total

ملحوظة: العدّاد ده مبسّط (conv وlinear بس، ومبيراعيش الـ groups). للمشاريع الحقيقية استخدم fvcore أو ptflops.

الخطوة ٣: Post-training static quantisation.

def quantise_ptq(model, calibration_loader, backend="x86"):
    import torch.ao.quantization as tq
    model = model.eval().cpu()
    model.qconfig = tq.get_default_qconfig(backend)    # 1) configure
    tq.prepare(model, inplace=True)                    # 2) نحط observers
    with torch.no_grad():
        for x, _ in calibration_loader:                # 3) calibrate ببيانات حقيقية
            model(x)
    tq.convert(model, inplace=True)                    # 4) convert لـ INT8
    return model

لازم الموديل يكون fused أولًا (Conv → BN → ReLU يبقوا وحدة واحدة) وده شغل torch.ao.quantization.fuse_modules.

def export_onnx(model, sample_input, path="model.onnx"):
    model = model.eval()
    torch.onnx.export(
        model, sample_input, path,
        input_names=["input"], output_names=["output"],
        dynamic_axes={"input": {0: "batch"}, "output": {0: "batch"}},   # batch متغير
        opset_version=17,
    )
    return path

الخطوة ٥: قارن الأنظمة.

from torchvision.models import mobilenet_v3_small

def compare_regimes():
    model = mobilenet_v3_small(weights=None, num_classes=10)
    params = parameter_count(model)
    flops = flops_estimate(model, (1, 3, 224, 224))
    lat = measure_latency(model, (1, 3, 224, 224), device="cpu")
    print(f"FP32 MobileNetV3-Small: {params:,} params  {flops/1e9:.2f} GFLOPs  "
          f"p50={lat['p50_ms']:.2f}ms  p95={lat['p95_ms']:.2f}ms")

إضافة مني: أخطاء شائعة وفين بتظهر في الـ LLMs والـ agents

  • القياس على الجهاز الغلط: أرقام الـ workstation مش تمثل Jetson أو موبايل. دايمًا اقيس على الـ target.
  • مقارنة FP32 بـ INT8 من غير نفس الـ pre-processing: الفرق في الـ resize والـ normalisation بيبان كخسارة دقة.
  • معايرة بداتا مش تمثيلية: لو الـ calibration set مختلف عن الداتا الحقيقية، النطاقات هتتظبط غلط والدقة تنزل أكتر من 1 نقطة.
  • ONNX tracing: الـ control flow اللي بيعتمد على القيم (if على tensor) مبيتصدّرش صح بالـ tracing؛ حوّله لـ ops أو استخدم torch.jit.script.
  • نفس المفاهيم في الـ LLMs: الـ quantisation (INT8/INT4) وdistillation والـ runtimes (llama.cpp، TensorRT-LLM) هي نفس الأفكار بالظبط، بس على الـ LLMs. وlatency في LLM بتتقسم لـ time-to-first-token وtokens/sec.
  • في الـ agents: agent بيشغّل vision tool محلي (OCR، detection) محتاج ميزانية latency واضحة؛ كل tool call بيزود زمن الخطوة، فاختيار موديل أصغر بيسرّع الـ loop كله.
