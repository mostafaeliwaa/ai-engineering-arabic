00

تسخين ٥ دقايق: فاكر الدرس اللي فات؟

الدرس اللي فات كان عن تدريب الموديل على أكتر من جهاز (rank). جاوب في دماغك وبعدين افتح الإجابة.

  1. في DDP، كل rank بيشتغل على إيه، وبعد الـ backward بيحصل إيه بالظبط؟
    الإجابةكل rank بيشغّل نفس الموديل على شريحة مختلفة من الـ batch. بعد الـ backward بيعملوا all_reduce للـ gradients ويقسموا على world_size، فكل rank يطلع بنفس الـ gradient قبل الـ optimizer step.
  2. ليه الـ parameters بتتعمل لها broadcast من rank 0 في أول التدريب؟
    الإجابةعشان كل الـ ranks يبدأوا بنفس الأوزان بالظبط. لو الأوزان اختلفت بين الـ ranks التدريب بيبوّظ بصمت من غير ما يطلع إيرور.
  3. الـ FSDP بيعمل إيه مختلف عن DDP؟
    الإجابةكل rank بيحتفظ بشريحة (shard) من كل parameter بس، والتنسور الكامل بيتجمّع (gather) وقت الـ forward للـ layer وبعدين بيتشال. بيوفر ذاكرة لما الموديل مش بيدخل على جهاز واحد.

01

المشكلة: موديل جديد كل أسبوع، وكله بيقول «أنا الأحسن»

كل أسبوع بينزل موديل لغة جديد، والإعلان بيقول إنه «شاطر». السؤال الصح: شاطر في إيه؟ الإجابة الأمينة إنك تبني leaderboard بنفسك، لأن الـ leaderboard بتاع الشركة هو اللي هما ظبطوا الموديل عليه.

من غير harness في الريبو بتقارن موديلين بالإحساس («حسّيت إن ده أحسن»). ومعاه بتقارن بـ درجة على مجموعة مهام ثابتة وبـ metric ثابتة، والنتيجة JSON تقدر تعمل لها diff. الـ harness هو العقد بين تشغيل إمبارح وتشغيل النهاردة. من غيره، الـ regressions بتتشحن للمستخدمين.

تشبيه: الـ harness زي امتحان موحّد للثانوية. كل الطلبة بنفس الأسئلة وبنفس ورقة التصحيح. لو كل مدرسة عملت امتحانها بنفسها، مش هتعرف مين شاطر فعلًا.

الفخ: إنك تظبط الـ harness على موديل واحد. العلاج إن كل قرار خاص بموديل معيّن يتحط في مكان واحد بس: الـ adapter. الباقي صغير لدرجة إنك تقراه في ١٥ دقيقة: المهام صغيرة وتتشحن في الريبو، والـ metrics مكتوبة من الصفر عشان زميلك يراجعها. ولو بدّلت الـ adapter الـ leaderboard يتحرك، ولو بدّلت المهام يتحرك، وأي حاجة تانية ماينفعش تحركه.

02

المفهوم: الـ pipeline كله في رسمة واحدة

task JSONLs → load_all_tasks → run_leaderboard → ModelAdapter.generate (batch) → METRIC_FNS → per-example score → task score → overall → leaderboard.json

خد بالك من الترتيب: الـ metric بتاخد ردّ الموديل وبتطلّع رقم بين 0 و1. الـ runner بيعمل متوسط الأرقام دي للمهمة، وبعدين متوسط درجات المهام هو الـ overall.

الـ Task spec: كل مثال سطر JSONL

{"id": "arith-00", "prompt": "compute: 2 + 2", "targets": ["4"], "metric": "exact_match"}

فيه أربع حقول أساسية: id وprompt وtargets (قايمة إجابات مقبولة) وmetric. وفيه حقل اختياري extras بيشيل بيانات جانبية للـ metric من غير ما تلوّث الـ prompt. مثال الكود:

{
  "id": "code-00",
  "prompt": "python: write a function f that doubles its input",
  "targets": ["ok"],
  "metric": "code_exec",
  "extras": {"io_pairs": [[1, 2], [3, 6]]}
}

المهمة = ملف .jsonl جوه outputs/tasks/، واسم الملف هو اسم المهمة. كل الأمثلة في الملف الواحد ليها نفس الـ metric (الـ runner بيعمل assert على ده). والسطور اللي بتبدأ بـ # والسطور الفاضية بيتخطاها الـ loader، عشان المساهمين يعلّقوا على الملفات.

عقد الـ Metric

كل metric دالة من (prediction, targets, extras) → float in [0.0, 1.0]. الـ harness بيعمل متوسط درجات الأمثلة = درجة المهمة، وبعدين متوسط درجات المهام = الـ overall. وكل metric صغيرة:

  • exact_match: lowercase، دمج المسافات المتكررة، وبعدين مساواة.
  • substring_contains: نفس التطبيع، لكن اختبار «موجود جوه» بدل المساواة.
  • multiple_choice: أول حرف في الرد (uppercase) لازم يكون من الحروف المسموحة.
  • rouge_l: طول الـ LCS مقسوم على طول التوقع وعلى طول المرجع، وبناخد الـ F1 بين الـ precision والـ recall.
  • code_exec: بننفّذ التوقع في namespace مقيّد، وننده f(x) على كل زوج input/output ونعدّ المطابقات.
ليه الرقم بين 0 و1؟ عشان المتوسطات تبقى قابلة للتفسير: ٠٫٨ يعني «٨٠٪» في أي مهمة، وتقدر تجمع مهام مختلفة جنب بعض.
أمان الـ code_exec: بتشغّل كود جاي من موديل، فبتديله __builtins__ مقلّصة لأسماء قليلة (range, len, min, max, abs, int, float). النتيجة إن import os بيفشل لأن الـ importer مش موجود، والسكور بيبقى 0.0 بدل ما الكود يتنفذ. (ده مش sandbox كامل زي الـ containers؛ هو حاجز بسيط يكفي للدرس.)
03

معمل ١: شوف الـ ROUGE-L بيتحسب إزاي

الـ LCS: أطول تسلسل مشترك

الـ LCS هو أطول تسلسل كلمات موجود في الجملتين بنفس الترتيب (مش لازم متلاصقين). الجدول اللي على الشمال هو جدول الـ dynamic programming: الصفوف كلمات التوقع (prediction) والأعمدة كلمات المرجع (reference)، وخانة الركن الأخير الشمال-تحت هي الطول النهائي.

بعدها: precision = lcs / len(pred) وrecall = lcs / len(ref) وF1 = 2·p·r / (p+r). الـ precision بتعاقبك على الكلام الزيادة، والـ recall بتعاقبك على اللي نسيته.

جرّب: حرّك السلايدر بين الأزواج. لاحظ إن «cats are warm blooded mammals» بتاخد recall كامل لكن precision أقل بسبب الكلمات الزيادة، وإن «mammals are cats» نفس الكلمات بس ترتيبها بوّظ الـ LCS.

الـ Adapter والـ Runner والـ Leaderboard

الـ Adapter: الوصلة الوحيدة مع الموديل

class ModelAdapter(Protocol):
    def generate(self, prompts: Sequence[str]) -> List[str]: ...
    @property
    def name(self) -> str: ...

الدرس بيجيب ToyAdapter: بيبصّ في بداية الـ prompt (compute: أو summarize: أو python:...) وبيرجّع الإجابة الصح لكل مثال في المهام الخمس. هدفه مش إنه «ذكي»، هدفه يدّي الـ harness مخرجات ثابتة يتحسب عليها السكور. ولما تيجي تقيس موديل حقيقي بتكتب adapter بيبعت الـ prompt لـ API وبيرجّع النص، والـ harness مش بيعرف الفرق.

تشبيه: الـ adapter زي مترجم في اجتماع. أي حد يتكلم بأي لغة، والـ harness بيسمع نفس الشكل (قايمة strings) دايمًا.

الـ Runner

run_task بياخد الأمثلة batch_size واحدة واحدة، ويبعتها للـ adapter، ويتأكد إن عدد المخرجات = عدد الـ prompts (وإلا بيرفع إيرور)، وبعدين بيحسب سكور كل مثال بالـ metric المناسبة ويقيس الـ latency. وبيطلّع TaskResult فيه: score وcorrect وtotal وlatency. أما run_leaderboard فبيلف على كل المهام (مرتبة بالاسم) ويحسب الـ overall = متوسط درجات المهام.

الـ Leaderboard JSON

write_leaderboard بيكتب JSON فيه schema (مثلًا leaderboard.v1) وtimestamp وoverall_score واسم الـ adapter وقايمة المهام. وجود حقل الـ schema مهم: لو غيّرت الشكل بعدين تغيّر النسخة، والداشبورد اللي بتقرا الملف يعرف يتصرف بدل ما يتكسر بصمت. ولو شغّلت بـ --include-per-example بتتحط معاها كل التوقعات عشان تعمل diff.

معمل ٣: الـ overall بيتحسب إزاي، والـ batching بيعمل إيه

متوسط المتوسطات

العمود الأول: درجة كل مهمة (حرّكها بالسلايدرز). الـ overall = متوسط درجات المهام الخمسة، يعني كل مهمة وزنها واحد بغض النظر عن عدد أمثلتها. ده قرار تصميم: مهمة فيها ٥ أمثلة وزنها زي مهمة فيها ٥٠٠.

خطوة ٢: التطبيع والـ metrics البسيطة

def normalize(s):                    # lowercase + مسافات مفردة
    return re.sub(r"\s+", " ", s.strip().lower())

def metric_exact_match(prediction, targets):
    p = normalize(prediction)
    return 1.0 if any(normalize(t) == p for t in targets) else 0.0

def metric_substring_contains(prediction, targets):
    p = normalize(prediction)
    return 1.0 if any(normalize(t) in p for t in targets) else 0.0

def metric_multiple_choice(prediction, targets):   # أول حرف بس
    pred = prediction.strip()[:1].upper()
    return 1.0 if pred in {t.strip()[:1].upper() for t in targets} else 0.0

خطوة ٣: ROUGE-L (الـ LCS + F1)

def _tokens(s):
    return re.findall(r"[a-z0-9]+", s.lower())

def _lcs_length(a, b):               # dynamic programming بصف واحد في الذاكرة
    if not a or not b:
        return 0
    prev = [0] * (len(b) + 1)
    for ai in a:
        cur = [0] * (len(b) + 1)
        for j, bj in enumerate(b):
            if ai == bj:
                cur[j + 1] = prev[j] + 1          # تطابق: زوّد على القطر
            else:
                cur[j + 1] = max(prev[j + 1], cur[j])   # خد الأحسن من فوق أو من الشمال
        prev = cur
    return prev[-1]

def metric_rouge_l(prediction, targets):
    pred = _tokens(prediction)
    if not pred:
        return 0.0
    best = 0.0
    for ref in targets:                         # أحسن مرجع من عدة مراجع
        r = _tokens(ref)
        lcs = _lcs_length(pred, r) if r else 0
        if lcs == 0:
            continue
        prec, rec = lcs / len(pred), lcs / len(r)
        best = max(best, 2 * prec * rec / (prec + rec))
    return best

خطوة ٤: code_exec في namespace مقيّد

def metric_code_exec(prediction, targets, extras):
    pairs = extras.get("io_pairs") or []
    if not isinstance(pairs, list) or not pairs:
        return 0.0
    safe_globals = {"__builtins__": {"range": range, "len": len, "min": min,
                                     "max": max, "abs": abs, "int": int, "float": float}}
    local = {}
    try:
        exec(prediction, safe_globals, local)   # import os هيفشل هنا
    except Exception:
        return 0.0
    fn = local.get("f")
    if not callable(fn):
        return 0.0
    correct = 0
    for x, expected in pairs:
        try:
            if fn(x) == expected:
                correct += 1
        except Exception:
            continue                            # خطأ في زوج واحد = صفر لزوج واحد
    return correct / len(pairs)

METRIC_FNS = {                                  # dispatch بالاسم
    "exact_match": lambda p, t, e: metric_exact_match(p, t),
    "substring_contains": lambda p, t, e: metric_substring_contains(p, t),
    "multiple_choice": lambda p, t, e: metric_multiple_choice(p, t),
    "rouge_l": lambda p, t, e: metric_rouge_l(p, t),
    "code_exec": lambda p, t, e: metric_code_exec(p, t, e),
}

خطوة ٥: تحميل المهام والـ Runner

def load_task_jsonl(path):
    out = []
    for n, raw in enumerate(path.read_text(encoding="utf-8").splitlines(), 1):
        raw = raw.strip()
        if not raw or raw.startswith("#"):       # تعليقات وسطور فاضية
            continue
        obj = json.loads(raw)
        out.append(Example(str(obj.get("id", f"ex-{n}")), obj["prompt"],
                           list(obj["targets"]), obj["metric"], dict(obj.get("extras", {}))))
    return out

def run_task(name, examples, adapter, batch_size=8):
    if batch_size <= 0:
        raise ValueError("batch_size must be > 0")
    metric = examples[0].metric
    assert all(e.metric == metric for e in examples), "task mixes metrics"
    fn, total_score, per = METRIC_FNS[metric], 0.0, []
    start = time.perf_counter()
    for i in range(0, len(examples), batch_size):
        chunk = examples[i:i + batch_size]
        outs = adapter.generate([e.prompt for e in chunk])
        if len(outs) != len(chunk):
            raise ValueError("adapter returned wrong number of outputs")
        for e, o in zip(chunk, outs):
            s = fn(o, e.targets, e.extras)
            total_score += s
            per.append({"id": e.id, "prediction": o, "score": s})
    ms = (time.perf_counter() - start) * 1000
    return TaskResult(name, metric, total_score / len(examples),
                      int(round(total_score)), len(examples), per, ms)

خطوة ٦: الـ Leaderboard وكتابة الـ JSON

def run_leaderboard(tasks, adapter, batch_size=8):
    results = [run_task(n, tasks[n], adapter, batch_size) for n in sorted(tasks)]
    overall = sum(r.score for r in results) / len(results) if results else 0.0
    return overall, results

def write_leaderboard(path, overall, results, adapter_name, include_per_example=False):
    payload = {"schema": "leaderboard.v1", "timestamp": time.time(),   # schema = نقطة الـ migration
               "overall_score": overall, "adapter": adapter_name,
               "tasks": [{"task": r.task, "metric": r.metric, "score": r.score,
                          "correct": r.correct, "total": r.total, "latency_ms": r.latency_ms,
                          **({"per_example": r.per_example} if include_per_example else {})}
                         for r in results]}
    path.write_text(json.dumps(payload, indent=2) + "\n")

    تلميحاكتب الدالة بنفس التوقيع (prediction, targets, extras) → float، وزوّدها في METRIC_FNS باسم جديد، واعمل ملف .jsonl بالاسم ده. مثلًا unigram overlap: عدد الكلمات المشتركة ÷ عدد كلمات التوقع. ماتنساش تكتب لها unit test صغير بحالات حدّية (توقع فاضي، مفيش تطابق).
  2. وسّع code_exec عشان يلتقط الـ stdout ويقبل قايمة stdout متوقعة كـ targets.
    تلميححوّل sys.stdout لـ io.StringIO وقت الـ exec (contextlib.redirect_stdout)، وبعدها قارن النص الملتقط بالـ target بعد normalize. مهم: لازم تضيف print للـ builtins المسموحة في الـ namespace وإلا الكود مش هيقدر يطبع.
  3. اعمل أمر diff للـ leaderboard: ياخد ملفي leaderboard.json ويطبع أنهي مهام اتحركت وبكام.
    تلميححمّل الملفين، ابني dict من task → score لكل واحد، والف على اتحاد الأسماء، واطبع الفرق new - old لو مش صفر. ماتنساش مهمة موجودة في ملف وناقصة في التاني، واطبع الـ overall كمان.
  4. حدّد latency أقصى لكل مثال: لف نداء الـ adapter بـ timeout واعرض عمود timeouts منفصل في الـ leaderboard.
    تلميحالأسهل concurrent.futures.ThreadPoolExecutor مع future.result(timeout=...). الـ timeout يتحسب «مثال فاشل» بدرجة صفر وعدّاد timeouts يزيد، من غير ما يوقف التشغيل كله.
  5. ثبّت محتوى المهام بـ sha256 داخل الـ leaderboard عشان أي حد بعدك يتأكد إنكم سكّرتوا نفس المهام.
    تلميحhashlib.sha256(path.read_bytes()).hexdigest() لكل ملف مهمة، وخزّنهم في حقل task_hashes (dict بالاسم) جنب الـ schema. وده بيسهّل فهم سبب تحرك السكور.
  6. تمرين إضافي مني (عملي): اعمل adapter ثاني اسمه FlakyAdapter بيجاوب صح أول ٣ أمثلة في كل batch وغلط الباقي، وشغّله بـ batch_size = 2 ثم 8 ثم 20. إيه اللي بيتغير في السكور ولماذا؟ وكمان اكتب اختبار بيثبت إن الـ runner يرفع إيرور لو الـ adapter رجّع عدد مخرجات غلط.
    الإجابةالسكور بيتغير لأن «أول ٣ في كل batch» بيتحسب حسب حدود الـ batch. كل مهمة فيها ٥ أمثلة: مع batch=2 الـ batches بتبقى ٢+٢+١ وكلها جوه أول ٣ فالسكور ١٫٠، ومع batch=8 أو 20 بيبقى batch واحد من ٥، فبيجاوب صح ٣ بس والسكور ٠٫٦. الدرس: سلوك الـ adapter لو اتأثر بحجم الـ batch يبقى الـ batch size جزء من نتيجة التقييم، ولازم تثبّته وتسجّله. اختبار الإيرور: adapter بيرجّع [] وpytest.raises(ValueError) حوالين run_task.

إضافة مني: اللي الدرس مش بيقوله

إضافة من عندي، مش من الدرس.
  • الحدس: الـ harness هو unit test للموديل. زي ما مش بتشحن كود من غير tests، متشحنش موديل (أو prompt جديد أو quantization) من غير ما تشغّل نفس المهام وتقارن بالرقم القديم.
  • أخطاء شائعة: (١) metric مرنة زيادة (substring_contains) بتدّي ١٫٠ لرد غلط فيه الكلمة صدفة. (٢) metric صارمة زيادة (exact_match) بتعاقب إجابة صح بصيغة مختلفة مثل «4.0» بدل «4». لاحظ إن الدرس نفسه بيستخدم target «25.0» للقسمة. (٣) عدد أمثلة قليل: ٥ أمثلة يعني كل مثال بـ ٢٠٪، والفرق بين موديلين ممكن يكون ضوضاء. (٤) تغيير المهام والـ adapter في نفس الوقت، فمتعرفش مين حرّك الرقم.
  • تسريب الـ test set (contamination): لو أمثلة التقييم دخلت في بيانات تدريب الموديل، الدرجة العالية مش معناها فهم. ولو ظبطت الـ prompts على الموديل لحد ما الدرجة تعلى، بقى الـ harness نفسه over-fitted. احتفظ بمهام «مخفية» ماتعدّلش عليها.
  • بيظهر فين في الـ LLMs والـ agents: نفس الشكل (task + metric + adapter + leaderboard) هو شكل lm-evaluation-harness وlighteval (المرجع اللي الدرس بيشاور عليه). وفي الـ agents بتتحول المهمة لـ «شغّل الـ agent وشوف الـ environment وصل للحالة المطلوبة؟»، والـ metric بقت «هل الاختبارات عدّت؟» (زي code_exec بالظبط).
