تسخين ٥ دقايق: فاكر امبارح؟

امبارح قطّعت الموديل stages وشغّلته كخط إنتاج. جاوب في دماغك، وبعدين افتح.

  1. N=4 stages و M=8 microbatches. الـ bubble كام؟ ولو M بقت 64؟
    الإجابة(N−1)/(M+N−1): عند M=8 تبقى 3/11 ≈ 27.27%، وعند M=64 تبقى 3/67 ≈ 4.48%. كتّر الـ microbatches والـ bubble يتخبّى.
  2. 1F1B بيكسب إيه على GPipe؟
    الإجابةنفس الـ bubble، بس ذاكرة الـ activations محدودة بعمق الـ pipeline (حوالي N) بدل عدد الـ microbatches (M)، لأن الـ backward بيبدأ بدري وبيفضّي الـ activations.
  3. ليه بنوازن الـ stages بالـ FLOPs مش بعدد الـ parameters؟ وإيه اللي بيعمل deadlock في الـ send/recv؟
    الإجابةأبطأ stage بتحكم كل cycle، والـ embedding فيها params كتير وحساب قليل. والـ deadlock بيحصل لو كل الـ stages عملت send قبل recv؛ الحل: الزوجي يبعت الأول والفردي يستقبل الأول.
الربط بالنهاردة: بعد ZeRO وبعد الـ pipeline، الحالة بقت متقطّعة على الـ ranks: كل واحد ماسك shard من الـ optimizer أو stage من الموديل. يبقى الـ checkpoint لازم يحفظ «مين ماسك إيه»، وإلا الحالة اللي اتحفظت مش هتتقري وقت الـ restart.

المشكلة: كل حاجة بتعدّي من باب واحد

الـ checkpoint التقليدي بيجمّع كل الـ parameters والـ optimizer state على rank 0، وبعدين rank 0 يكتب ملف واحد. لموديل 70B ده 1.1 TB من الحالة بتعدّي من network port واحد. وطول ما rank 0 بيكتب، باقي الـ ranks قاعدين مستنيين الـ gather. سرعة الكتابة بقت سرعة أبطأ link لـ GPU واحدة، مش مجموع الـ cluster.

زي مول فيه ٦٤ محل، وكل المحلات لازم تطلّع بضاعتها من باب واحد بس. على cluster حقيقي، خطوة الـ gather-then-write ممكن تاخد أطول من ساعة التدريب اللي قبلها، يعني الـ job بيلحق يعمل أقل من checkpoint واحد في يوم التدريب.

الـ sharded checkpoint بيقلب الفكرة: كل rank بيكتب الـ shard بتاعه في ملفه بالتوازي، والـ manifest بيسجّل مين كان ماسك أنهي shard عشان الـ resume يرجّع كل حاجة مكانها. سرعة الكتابة الإجمالية بتكبر مع حجم الـ cluster: checkpoint حجمه 1 TB كان بياخد ٤ ساعات من rank واحد، بياخد حوالي ٤ دقايق من ٦٤ rank.

معمل ١: باب واحد ولا ٦٤ باب؟

اختار حجم الحالة وعدد الـ ranks وسرعة الكتابة لكل rank، ودوس «اكتب» وشوف الاتنين بيتسابقوا.

تبسيط: المعمل بيفترض إن الـ storage يستحمل الكتابة المتوازية كلها. في الحقيقة الـ filesystem له حد، وعشان كده الـ parallel filesystems زي Lustre و GPFS بتعمل striping. الافتراضي هنا قريب من مثال الدرس: 1 TB في حوالي ٤ ساعات من rank واحد.

الـ Manifest: عقد بين الكاتب والقارئ

الـ shard files لوحدها مجرد bytes. الـ manifest هو اللي بيقول للـ loader «اتوقّع إيه» قبل ما يلمس الحالة:

{
  "world_size": 4,
  "step": 1234,
  "wall_clock_seconds": 4521,
  "shards": [
    {"rank": 0, "path": "rank0.bin", "sha256": "...", "param_shard_offset": 0, "param_shard_numel": 65536},
    {"rank": 1, "path": "rank1.bin", "sha256": "...", "param_shard_offset": 65536, "param_shard_numel": 65536}
  ],
  "schema_version": 1
}

فيه ٣ حقول شايلة الشغل كله:

  • world_size: لو حاولت تعمل resume على عدد ranks مختلف، يفشل بصوت عالي بدل ما يبوّظ الحالة في السكوت.
  • sha256 لكل shard: بيمسك الكتابة الناقصة أو الملف البايظ.
  • param_shard_offset و param_shard_numel: بيخلّوا الـ loader يحط كل shard في مكانه الصح جوه الـ flat parameter tensor.

الـ Atomic write: اكتب في .tmp، وبعدين rename

الترتيب: اكتب كل shard في <name>.tmp، اكتب الـ manifest في manifest.json.tmp، اعمل fsync لكل واحد، اعمل rename للـ shards، والـ manifest آخر واحد.

الـ rename الواحد في POSIX على نفس الـ filesystem atomic: يا الملف الجديد موجود كامل، يا القديم لسه موجود. بس مجموعة renames مش transaction. عشان كده rename الـ manifest هو «لحظة الـ commit»، والـ loader بيراجع كل shard على الـ hashes اللي في الـ manifest.

والنقطة اللي ناس كتير بتغلط فيها: اكتب كل checkpoint في فولدر خاص بالـ step بتاعه (step_0200/). كده لو حصل crash قبل rename الـ manifest، الـ checkpoint اللي قبله يفضل هو الشغال. لو استخدمت نفس الفولدر كل مرة، الضمان ده بيتكسر: الـ shard renames بتبدّل الـ shards القديمة قبل ما الـ manifest الجديد يوصل.

زي إنك بتكتب مذكرة جديدة في كشكول جديد، وتقطع الصفحة القديمة من الفهرس بس لما الجديدة تخلص. لو كتبت فوق القديمة على طول وانقطعت الكهربا، مش هيبقى معاك لا القديم ولا الجديد.

معمل ٢: اقطع الكهربا في أي لحظة

فيه checkpoint سليم عند step 100، وإنت بتحفظ step 200. اختار الطريقة، وحرّك «الـ crash بعد خطوة» لأي نقطة، وشوف الـ resume هيلاقي إيه.

جرب: (١) «فولدر لكل step» مع crash في أي نقطة: دايمًا فيه checkpoint سليم. (٢) «نفس الفولدر + tmp»: crash بعد rename الـ shard الأول = مفيش ولا checkpoint سليم. (٣) «كتابة مباشرة» واقفل فحص الـ sha256: الـ resume بيعدّي وهو بايظ.

      ٣ حاجات بتخلّي الـ checkpoint يتشحن

      1. Async write. الـ production بيبعت الكتابة على thread أو process منفصل عشان التدريب يكمّل. الحاجز عند الـ checkpoint اللي بعده: ما تبدأش save جديد قبل ما اللي قبله يخلص. الـ flag async_io في DeepSpeed بيعمل كده. الدرس بيخلّي الكتابة synchronous عشان الخطوات تبان.
      2. ديسك محلي سريع الأول، وبعدين upload في الخلفية. اكتب على NVMe محلي، وارفع async على S3 أو GCS. كده الـ checkpoint جوه الـ cluster سريع للـ resume، وفيه نسخة دايمة بره للأرشيف. الـ manifest بيشيل المسار المحلي، و upload manifest بيشيل المسار البعيد.
      3. الـ Rotation. احتفظ بآخر K checkpoints (غالبًا ٣ لـ ٥) وامسح الأقدم. من غيرها الديسك بيتملي في نص الـ run والـ checkpoint اللي بعده يفشل.

      SCHEMA_VERSION = 1
MANIFEST_NAME = "manifest.json"

@dataclass
class ShardEntry:
    rank: int
    path: str
    sha256: str
    param_shard_offset: int
    param_shard_numel: int

@dataclass
class ShardManifest:
    world_size: int
    step: int
    wall_clock_seconds: float
    shards: list
    schema_version: int = SCHEMA_VERSION

    def to_json(self):
        return json.dumps({
            "world_size": self.world_size, "step": self.step,
            "wall_clock_seconds": self.wall_clock_seconds,
            "schema_version": self.schema_version,
            "shards": [asdict(s) for s in self.shards],
        }, indent=2, sort_keys=True)          # sort_keys = ناتج ثابت

    @classmethod
    def from_json(cls, text):
        d = json.loads(text)
        return cls(world_size=int(d["world_size"]), step=int(d["step"]),
                   wall_clock_seconds=float(d["wall_clock_seconds"]),
                   schema_version=int(d["schema_version"]),
                   shards=[ShardEntry(**s) for s in d["shards"]])

class CheckpointError(Exception):

      def _sha256_bytes(data):
    return hashlib.sha256(data).hexdigest()

def _fsync_dir(path):
    # fsync للفولدر نفسه عشان الـ rename يوصل للديسك؛ ولو مش مدعوم يعدّي
    try:
        fd = os.open(str(path), os.O_RDONLY)
    except OSError:
        return
    try:
        os.fsync(fd)
    except OSError:
        pass
    finally:
        os.close(fd)

def _serialize_state(state):
    buf = io.BytesIO()
    torch.save(state, buf, pickle_protocol=4)
    return buf.getvalue()

def _deserialize_state(data):
    return torch.load(io.BytesIO(data), weights_only=False)

      خطوة ٣: save_sharded بالـ tmp + rename

      def save_sharded(per_rank_state, dest_dir, step, wall_clock_seconds=0.0):
    dest = Path(dest_dir)
    dest.mkdir(parents=True, exist_ok=True)
    shards, tmp_paths, offset = [], [], 0
    for rank, state in enumerate(per_rank_state):
        payload = _serialize_state(state)
        sha = _sha256_bytes(payload)              # الـ hash على الـ bytes اللي هتتكتب
        tmp_path = dest / f"rank{rank}.bin.tmp"
        with open(tmp_path, "wb") as f:
            f.write(payload)
            f.flush()
            os.fsync(f.fileno())                  # اتأكد إن الـ bytes نزلت الديسك
        tmp_paths.append((tmp_path, dest / f"rank{rank}.bin"))
        ps = state.get("param_shard")
        numel = ps.numel() if isinstance(ps, torch.Tensor) else 0
        shards.append(ShardEntry(rank, f"rank{rank}.bin", sha, offset, numel))
        offset += numel                           # الـ shard اللي بعده يبدأ هنا
    manifest = ShardManifest(len(per_rank_state), step, wall_clock_seconds, shards)
    manifest_tmp = dest / (MANIFEST_NAME + ".tmp")
    with open(manifest_tmp, "w") as f:
        f.write(manifest.to_json())
        f.flush()
        os.fsync(f.fileno())
    for tmp, final in tmp_paths:
        os.replace(tmp, final)                    # rename atomic لكل shard
    os.replace(manifest_tmp, dest / MANIFEST_NAME) # لحظة الـ commit: الـ manifest آخر واحد
    _fsync_dir(dest)
    return manifest

      خطوة ٤: load_sharded: افحص كل حاجة قبل ما تلمس الحالة

      def load_sharded(src_dir, expected_world_size):
    src = Path(src_dir)
    mp = src / MANIFEST_NAME
    if not mp.exists():
        raise CheckpointError(f"manifest missing at {mp}")
    m = ShardManifest.from_json(mp.read_text())
    if m.world_size != expected_world_size:                 # failure mode ١
        raise CheckpointError(f"world_size mismatch: manifest={m.world_size}, expected={expected_world_size}")
    if m.schema_version != SCHEMA_VERSION:
        raise CheckpointError(f"schema_version mismatch: manifest={m.schema_version}, expected={SCHEMA_VERSION}")
    if len(m.shards) != m.world_size:                        # failure mode ٢
        raise CheckpointError(f"shard count != world_size: {len(m.shards)} vs {m.world_size}")
    per_rank, seen, src_resolved = [None] * m.world_size, set(), src.resolve()
    for s in m.shards:
        if not (0 <= s.rank < m.world_size):
            raise CheckpointError(f"shard rank {s.rank} out of range [0,{m.world_size})")
        if s.rank in seen:
            raise CheckpointError(f"duplicate shard for rank {s.rank}")
        seen.add(s.rank)
        # أمان: ممنوع path مطلق أو فيه / أو .. عشان محدش يخلّيك تقرا ملف بره الفولدر
        if os.path.isabs(s.path) or os.sep in s.path or "/" in s.path or s.path in ("", ".", ".."):
            raise CheckpointError(f"unsafe shard path: {s.path!r}")
        shard_path = (src / s.path).resolve()
        try:
            shard_path.relative_to(src_resolved)
        except ValueError as exc:
            raise CheckpointError(f"shard path escapes checkpoint dir: {s.path!r}") from exc
        if not shard_path.exists():
            raise CheckpointError(f"shard file missing: {shard_path}")
        payload = shard_path.read_bytes()
        actual = _sha256_bytes(payload)
        if actual != s.sha256:                               # failure mode ٣
            raise CheckpointError(f"sha256 mismatch on rank {s.rank}: "
                                  f"recorded={s.sha256[:12]}..., actual={actual[:12]}...")
        per_rank[s.rank] = _deserialize_state(payload)
    if len(seen) != m.world_size:
        missing = sorted(set(range(m.world_size)) - seen)
        raise CheckpointError(f"manifest missing ranks: {missing}")
    return m, per_rank

      خطوة ٥: rotate_checkpoints

      def rotate_checkpoints(parent_dir, keep_last=5):
    if keep_last < 0:
        raise ValueError(f"keep_last must be >= 0, got {keep_last}")
    parent = Path(parent_dir)
    if not parent.exists():
        return []
    children = sorted(
        [c for c in parent.iterdir() if c.is_dir() and c.name.startswith("step_")],
        key=lambda c: (c.stat().st_mtime, c.name),   # الأقدم الأول
    )
    if keep_last == 0:
        to_delete = children
    elif len(children) > keep_last:
        to_delete = children[:-keep_last]
    else:
        to_delete = []
    for c in to_delete:
        shutil.rmtree(c, ignore_errors=True)
    return [c.name for c in to_delete]

      التمارين

      1. Async write: ابدأ الـ save في thread وخلّي التدريب يكمّل، وامنع الـ save اللي بعده لحد ما اللي قبله يخلص.
        تلميحخد snapshot الأول ({k: v.clone()}) عشان التدريب ما يغيّرش الـ tensors وهي بتتكتب. خزّن الـ threading.Thread في متغير، وقبل أي save جديد اعمل prev.join().
      2. Rotation بـ last_5_steps: احتفظ بآخر ٥ وامسح الأقدم قبل ما تحفظ الجديد.
        تلميحrotate_checkpoints(parent, keep_last=4) قبل الـ save يسيب مكان للجديد، فيبقى المجموع ٥. خد بالك: لو الـ save الجديد فشل، هيبقى معاك ٤ بس. فكّر: تمسح قبل ولا بعد؟
      3. فحص سريع بـ CRC للـ reload في الـ inner loop بدل sha256 الكامل.
        تلميحzlib.crc32(payload) أسرع بكتير. سجّل الاتنين في الـ manifest، واستخدم الـ CRC في المسار السريع والـ sha256 في الـ resume الحقيقي. الـ CRC بيمسك الـ corruption العشوائي، بس مش معمول ضد التلاعب المقصود.
      4. Load على world size مختلف: rebalance من N=4 لـ N=8.
        تلميحرتّب الـ shards بالـ param_shard_offset، اعمل torch.cat لكل نوع (param, m, v)، وبعدين chunk(8) مع padding لو الطول مش بيقبل القسمة. اكتبه كدالة منفصلة صريحة، مش جوه load_sharded، عشان الرفض العالي يفضل هو الافتراضي.
      5. Upload لـ fake S3 (فولدر تاني) واكتب upload manifest، ودافع عن سياسة التخزين على مستويين.
        تلميحانسخ الملفات للفولدر التاني بنفس الـ tmp + rename، واكتب upload_manifest.json فيه المسار البعيد والـ sha256. الدفاع: المحلي سريع للـ resume، والبعيد بيعيش لو الـ node نفسها ماتت.
      6. إضافة مني · latest + أحدث checkpoint سليم: اكتب ملف latest (atomic برضه) فيه اسم آخر فولدر خلص، واكتب find_latest_valid(parent, world_size) تبدأ منه وترجع لورا لحد ما تلاقي checkpoint يعدّي load_sharded. ده بالظبط اللي بتحتاجه في الـ auto-restart script بتاع أي job تدريب.
        تلميحرتّب الفولدرات step_* تنازلي. لكل واحد جرّب load_sharded جوه try/except CheckpointError، واطبع سبب الرفض في الـ log. ما تمسحش الفولدر البايظ أوتوماتيك؛ سيبه للتحقيق.
      07

      إضافة مني: اللي الدرس ما قالوش

      الحدس في سطر: الـ checkpoint الكويس مش اللي «بيتحفظ»، ده اللي بيرفض يتحمّل وهو بايظ. كل حقل في الـ manifest موجود عشان يدّي الـ loader سبب يقول «لأ».

      أخطاء شائعة

      • torch.load(weights_only=False) = pickle. الكود بيعمل كده عشان الـ state فيه أنواع عادية. ده تمام لملفات إنت كاتبها، بس pickle ممكن ينفّذ كود وقت التحميل. أي checkpoint جاي من بره (من النت مثلًا) حمّله بـ weights_only=True أو بصيغة زي safetensors. فحص الـ path اللي في الدرس بيحميك من قراية ملف بره الفولدر، لكن مش من pickle خبيث.
      • الـ tmp لازم يكون على نفس الـ filesystem. الـ rename atomic بس جوه نفس الـ filesystem. لو كتبت الـ tmp في /tmp والنهائي على ديسك تاني، العملية بتبقى copy + delete ومش atomic. الدرس حاطط الـ tmp جنب الملف النهائي، وده الصح.
      • الأوزان لوحدها مش resume كامل. عشان التدريب يكمّل «كأن مفيش حاجة حصلت» محتاج كمان: رقم الـ step، حالة الـ LR scheduler، مكان الـ dataloader في الداتا، وحالة الـ RNG. الـ demo فيه step بس؛ في شغل حقيقي ضيف الباقي في نفس الـ state dict.
      • إنك تنسى fsync للفولدر. الـ fsync للملف بيضمن الـ bytes، لكن الـ rename نفسه metadata في الفولدر. عشان كده فيه _fsync_dir في الآخر.

      بيظهر فين في الـ LLMs والـ agents

      أي تدريب طويل لـ LLM بيعيش على الـ checkpoints دي. ونفس الأفكار (اكتب في tmp، commit في الآخر، افحص قبل ما تحمّل، احتفظ بآخر K) بتظهر في الـ agents اللي بتحفظ حالتها بعد كل خطوة عشان تكمّل لو اتقطعت، وفي أي service بتكتب ملفات حالة على الديسك.
