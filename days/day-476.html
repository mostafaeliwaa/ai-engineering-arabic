01

المشكلة: الداتا كبيرة، والموديل (ساعات) كمان

الموديل بيدخل جهاز واحد، لكن الداتا لا. وانت عايز تشوف أمثلة أكتر N مرة في نفس الوقت. أول مقبض: Data Parallel. كل rank (عملية) بيشغّل نفس الموديل على شريحة مختلفة من الـ batch، وبعدين الـ gradients بتتعمل لها متوسط قبل الـ optimizer step.

تاني مقبض: FSDP (Fully Sharded Data Parallel). الموديل نفسه مبيدخلش جهاز واحد، فكل rank بيمسك جزء من كل parameter، ويجمّع التنسور الكامل طبقة بطبقة وقت الـ forward.

تشبيه: فريق من ٤ مدرّسين بيصححوا امتحان ٤٠٠ ورقة. كل واحد بياخد ١٠٠ ورقة (Data Parallel). في الآخر بيجمعوا متوسط الدرجات ويتفقوا كلهم على نفس النتيجة (all-reduce). ولو الدليل نفسه (الموديل) ضخم مينفعش كل واحد يشيله كله، كل واحد بيشيل فصل منه وبيبعتوه لبعض لما حد يحتاجه (FSDP).

الوجع في الـ bookkeeping: لو الـ parameters اختلفت بين الـ ranks، التدريب بايظ بصمت. لو عملت متوسط للـ gradients ومعملتش للـ loss، الـ dashboard بيكدب. ولو الـ backend مقدرش يتفق على topology، التدريب بيعلّق للأبد. الحل: اكتب الـ collectives بإيدك مرة، وماتثقش في wrapper مش قادر تعيد تكوينه.

الدرس بيشتغل على CPU ومن غير CUDA. الـ gloo backend جاي مع أي PyTorch ويقبل workers من torch.multiprocessing. على node فيها GPUs كتير نفس الكود بيتحوّل لـ nccl من غير ما الهيكل يتغير.

الـ collectives الثلاثة

Collectiveبتعمل إيهإمتى
broadcastتنسور من rank واحد لكل الباقيinit الـ parameters، حالة الـ scheduler، أي مزامنة من واحد للكل
all_reduceتجمع (أو متوسط أو max) تنسور عبر كل الـ ranks، وكل rank بياخد النتيجةمتوسط الـ gradients بعد الـ backward
all_gatherكل rank بيساهم بتنسور، وكل rank بيستلم التجميعة كلهاجمع logits، وفك تجميع الـ parameters في FSDP (unshard)

عقد الـ DDP: broadcast وقت البناء + all_reduce بعد الـ backward. والـ FSDP بيضيف all_gather قبل forward كل طبقة.

init → broadcast من rank 0 → [لكل step: شريحة batch لكل rank → forward + backward محلي → all_reduce للـ grads ÷ world_size → optimizer.step على كل rank]

معمل ١: دورة الـ DDP

اضغط «التالي» وتابع إيه اللي بيحصل بين rank 0 وrank 1 في بداية التدريب وفي كل step.

لاحظ: بعد الـ all-reduce كل الـ ranks عندهم نفس الـ gradient، فنفس الـ optimizer step على نفس الـ parameters بتطلّع نفس النتيجة. عشان كده الـ parameters بتفضل متطابقة من غير ما نبعتها تاني.
02

إثبات: متوسط الـ gradients = gradient الـ batch الكبير

موديل متدرّب على batch حجمه B على N ranks لازم يطلّع نفس الـ gradient اللي عملية واحدة هتطلّعه على batch حجمه N×B. السبب: الـ cross entropy بـ mean reduction على الـ batch الكامل = متوسط المتوسطات اللي حسبها كل rank. فجمع الـ gradients وقسمتها على N بيدّي متوسط gradient الـ loss بالظبط.

الاختبار manual_all_reduce_matches_single_process بيبني نفس الموديل على rank 0 ويقارن الـ gradient بعد الـ all-reduce بالـ gradient المرجعي على input متجمّع. الفرق بيطلع حوالي 1e-8 والـ assert عند 1e-3.

معمل ٢: المتوسط على الأجهزة

عندنا ٨ أمثلة، لكل واحد gradient (أرقام ثابتة للتجربة). غيّر عدد الـ ranks. كل rank بيحسب متوسط شريحته، وفي الآخر بنعمل متوسط المتوسطات. قارنه بمتوسط الـ batch كله.

لاحظ: لما الأمثلة تتقسم بالتساوي (١ و٢ و٤ و٨) المتوسطين بيتطابقوا. لو التقسيم مش متساوي (٣ مثلًا) المتوسط البسيط للمتوسطات بيختلف، لأن rank معاه أمثلة أكتر أخد وزن غلط. دي ملحوظة مني مش في الدرس: الدرس بيستخدم batches بنفس الحجم.
03

FSDP: كل rank بيشيل شريحة من كل parameter

كل parameter بيتقسم لـ N شرايح مسطّحة (flat) متساوية، وكل rank بيحتفظ بشريحته بس. قبل الـ forward بتاع طبقة، بنعمل all_gather فكل rank بيبني التنسور الكامل. بعد الـ forward بنرمي النسخة الكاملة ونحتفظ بالشريحة بس.

مكسب الذاكرة دقيق: ذاكرة الـ parameters لكل rank تنزل لـ 1/N. التكلفة هي الـ gather اللي بتتدفع في كل forward. الـ FSDP الحقيقي بيغطي الـ gather بحساب الطبقة اللي قبلها (overlap) فتكلفة الوقت بتبقى أقل بكتير من الحساب الساذج.

تشبيه: مكتبة ضخمة مفيش كشك واحد بيشيل كل الكتب. كل كشك بيشيل رف من كل قسم، ولما حد عايز كتاب من قسم بيتجمّع الرف من كل الأكشاك، يقراه، ويرجّع الرف.

تفصيلة الـ padding: الـ all_gather في gloo (وفي nccl كمان) بيتوقع تنسورات خرج بنفس الحجم من كل rank. لو طول الـ parameter مش بيقبل القسمة على world_size، بنزوّد أصفار في الآخر (padding) لحد أقرب مضاعف، بنقسم، وبعد الـ gather بنشيل الـ padding. الدرس بيعمل round-trip على كل parameter وبيتأكد إن الـ reconstruction بيطابق الأصل.

معمل ٣: الـ shard والـ padding والذاكرة

جرّب طول parameter وعدد ranks. شوف حجم الـ shard والـ padding المطلوب، وبعدها الحاسبة التانية للذاكرة: DDP (كل rank عنده نسخة كاملة) ضد FSDP (١/N من الـ parameters).

معمل ٤: خطوات الـ unshard

اضغط «التالي» وتابع طريق الـ parameter الواحد في الـ forward.

gloo ضد nccl

الـ CUDA هو هدف الـ production، لكن نفس المسارات موجودة على CPU. الـ gloo هو backend الـ CPU، وأبطأ من nccl على الـ GPUs بمراحل، بس شكل الـ API نفسه. الدرس بيبدأ الـ process group بـ backend="gloo" ويشغّل الـ ranks بـ torch.multiprocessing بدل torchrun، والاتنين بيوصلوا لنفس نداءات torch.distributed. على node فيها GPUs: غيّر لـ backend="nccl"، استخدم device tensors، وشغّل بـ torchrun.

إزاي ده بيتستخدم في الحقيقي

  • الـ DistributedDataParallel الحقيقي بيضيف: hooks بعد الـ backward بتغطي الـ all-reduce بباقي الـ backward، وbucketed all-reduce بيجمع عدة gradients صغيرة في collective واحد، والـ no_sync اللي شفناها في درس ٤٧٤.
  • الـ FSDP الحقيقي بيضيف: view مسطّح لكل طبقة (buffer متصل)، وgather الطبقة الجاية بيتغطى بحساب الطبقة الحالية، وCPU offload اختياري للـ shards.
  • الشكل واحد: broadcast في البداية، reduce بعد الـ backward، وshard للـ parameters لما متبقاش تدخل.

خطوة ١: بناء الـ process group

import os, sys
import torch
import torch.distributed as dist
from torch import nn

def init_process_group(rank, world_size, backend, master_port):
    os.environ["MASTER_ADDR"] = "127.0.0.1"     # كل rank بيطرق نفس الـ host
    os.environ["MASTER_PORT"] = str(master_port)   # ونفس الـ port (rendezvous)
    loopback = "lo0" if sys.platform == "darwin" else "lo"
    os.environ.setdefault("GLOO_SOCKET_IFNAME", loopback)  # نخلي gloo يستخدم loopback
    os.environ.setdefault("TP_SOCKET_IFNAME", loopback)
    dist.init_process_group(backend=backend, rank=rank, world_size=world_size)

def shutdown_process_group():
    if dist.is_initialized():
        dist.destroy_process_group()

def free_port():                                 # نختار port فاضي بالـ bind-and-close
    import socket
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.bind(("127.0.0.1", 0))
    port = s.getsockname()[1]
    s.close()
    return port

خطوة ٢: الموديل والـ broadcast

def make_model(in_dim, hidden, out_dim):
    return nn.Sequential(nn.Linear(in_dim, hidden), nn.GELU(),
                         nn.Linear(hidden, out_dim))

def broadcast_module(module, src=0):
    for tensor in list(module.parameters()) + list(module.buffers()):
        dist.broadcast(tensor.data, src=src)     # قيم rank 0 هي الـ init الرسمي

من غير الـ broadcast كل rank بيعمل init بـ seed بتاعه، والـ ranks بتبعد عن بعض من أول step.

خطوة ٣: الـ all-reduce للـ gradients

def all_reduce_grads_(module, world_size):
    total_sq = 0.0
    for p in module.parameters():
        if p.grad is None:
            p.grad = torch.zeros_like(p.data)    # لازم كل rank يشارك حتى لو grad فاضي
        dist.all_reduce(p.grad.data, op=dist.ReduceOp.SUM)   # اجمع
        p.grad.data.div_(world_size)                         # واقسم = متوسط
        total_sq += float(p.grad.data.pow(2).sum().item())
    return total_sq ** 0.5                       # L2 norm للـ log

لو rank ما شاركش في الـ all-reduce (مثلًا grad فاضي وما عملش الصفر) الباقيين هيعلّقوا. عشان كده الـ zeros_like.

خطوة ٤: تقسيم الـ batch والـ MinimalDDP

def shard_for_rank(x, rank, world_size):
    total = x.shape[0]
    per = total // world_size
    remainder = total - per * world_size
    start = rank * per + min(rank, remainder)       # أول ranks بتاخد مثال زيادة
    end = start + per + (1 if rank < remainder else 0)
    return x[start:end]

class MinimalDDP(nn.Module):
    def __init__(self, module, world_size):
        super().__init__()
        self.module = module
        self.world_size = world_size
        if dist.is_initialized() and world_size > 1:
            broadcast_module(self.module, src=0)    # عقد ١: broadcast وقت البناء

    def forward(self, *args, **kwargs):
        return self.module(*args, **kwargs)

    def sync_grads(self):                           # عقد ٢: بعد الـ backward
        if not dist.is_initialized() or self.world_size == 1:
            return _grad_norm(self.module)
        return all_reduce_grads_(self.module, self.world_size)

def _grad_norm(module):
    total_sq = 0.0
    for p in module.parameters():
        if p.grad is not None:
            total_sq += float(p.grad.data.pow(2).sum().item())
    return total_sq ** 0.5

حلقة التدريب في كل rank بتبقى: خُد شريحتك بـ shard_for_rank، loss.backward()، ddp.sync_grads()، optimizer.step(). الـ rank_main في الأصل بيعمل ده وبيرجّع RankResult فيها param sums وlosses. والـ run_distributed_demo بتولّد الـ ranks بـ torch.multiprocessing.

خطوة ٥: الـ FSDP round trip

def fsdp_round_trip_sketch(module, world_size, rank):
    ok = True
    for p in module.parameters():
        full = p.data.detach().clone()
        flat = full.flatten()
        total = flat.numel()
        per = (total + world_size - 1) // world_size      # ceil
        pad = per * world_size - total
        padded = torch.cat([flat, torch.zeros(pad, dtype=flat.dtype)]) if pad > 0 else flat
        my_slice = padded[rank * per:(rank + 1) * per].clone()   # شريحتي بس
        gathered = [torch.empty(per, dtype=flat.dtype) for _ in range(world_size)]
        dist.all_gather(gathered, my_slice)               # unshard
        rebuilt = torch.cat(gathered)[:total].view_as(full)   # شيل الـ padding
        if not torch.allclose(rebuilt, full):
            ok = False
            break
    return ok

ده الـ unshard. الـ re-shard العكسي (بعد الـ forward) هو مجرد slice تاني من التنسور المجمّع.

التمارين

  1. شغّل بـ --world-size 4 وتأكد إن فرق الـ parameters بين الـ ranks فاضل تحت 1e-3 طول التدريب.
    تلميح / إجابةشغّل الأمر من الأعلى بدون --no-write وافتح outputs/ddp-demo.json، وبص على param_sum_spread. المفروض قريب من صفر. لو كبر، يبقى أحد العقدين (broadcast أو all-reduce) مش شغّال.
  2. استبدل المتوسط اليدوي بـ dist.all_reduce(op=dist.ReduceOp.AVG) وقِس الفرق في الوقت.
    تلميح / إجابةاكتب النسختين وقِس بـ time.perf_counter() حوالين ١٠٠ استدعاء. ممكن الـ AVG مدعوم في backends معينة وغير مدعوم في غيرها (جرّبه على gloo وشوف). الأرقام هتختلف حسب الجهاز، فاعتمد على قياسك.
  3. ضيف hook بعد الـ backward في الـ wrapper عشان الـ all-reduce يتغطى بباقي الـ backward، وقِس التحسّن في وقت الـ wallclock.
    تلميح / إجابةاستخدم p.register_post_accumulate_grad_hook(fn) على كل parameter (في PyTorch الحديث) واعمل dist.all_reduce(p.grad, async_op=True) واحتفظ بالـ handles. قبل الـ optimizer step اعمل wait() لكلهم وبعدين اقسم على world_size. على CPU التغطية ممكن تبقى محدودة.
  4. نفّذ خطوة الـ re-shard في FSDP: بعد الـ forward استبدل التنسور الكامل بالشريحة المحلية وتأكد إن الذاكرة لكل rank بتنزل.
    تلميح / إجابةخزّن p.data = my_slice بعد الـ forward واحتفظ بالشكل الأصلي لوحده. قبل الـ forward الجاية اعمل all_gather وارجع الشكل. قيس numel() للـ parameters المخزّنة على كل rank: لازم يبقى حوالي 1/world_size.
  5. غيّر الـ backend لـ nccl على جهاز CUDA. إيه متغيرات البيئة اللي بتتغير واللي بتفضل؟
    تلميح / إجابةالـ MASTER_ADDR وMASTER_PORT بيفضلوا. متغيرات الـ gloo زي GLOO_SOCKET_IFNAME مش بتفيد، وnccl ليه متغيراته (زي NCCL_SOCKET_IFNAME). كمان التنسورات لازم تبقى على الـ GPU بـ .cuda(). وفي الـ production بتشغّل بـ torchrun اللي بيحدد الـ rank والـ world size من البيئة.
  6. تمرين إضافي مني: اعمل سيناريو «rank واحد بيعلّق» عن قصد: خلّي rank 1 يتخطى sync_grads() في step معيّن، وشوف إيه اللي يحصل (ضيف timeout).
    تلميح / إجابةمرّر timeout=datetime.timedelta(seconds=10) لـ init_process_group. الـ rank 0 هيستنّى في الـ all-reduce لحد ما الـ timeout يخلص ويطلّع إيرور (أو يعلّق لو الـ timeout كبير). ده بيوريك ليه كل الـ ranks لازم تنده نفس الـ collectives بنفس الترتيب.

القسم ده من عندي عشان يكمّل الصورة. مش جزء من docs الدرس.
  • ليه الـ ranks بتفضل متطابقة من غير ما نبعت الـ parameters؟ لأن الـ optimizer step دالة حتمية في (الـ parameters، الـ gradient، حالة الـ optimizer). لو الثلاثة متطابقين في البداية، والـ gradient متطابق بعد الـ all-reduce، فالنتيجة متطابقة. مصدر الـ drift الوحيد هو عدم التطابق في أي واحدة منهم، ومنها العشوائية (dropout مثلًا) لو الـ seeds اختلفت بين الـ ranks فلازم الـ batch والـ gradient يتعاملوا بحذر.
  • الـ world_size يدخل في الـ effective batch: الـ effective_batch = micro_batch × accum_steps × world_size (درس ٤٧٤). والـ DDP + الـ accumulation معاهم no_sync بيوفروا N-1 all-reduce.
  • الـ checkpoint (درس ٤٧٥): في DDP عادةً rank 0 هو اللي بيكتب الـ checkpoint (لأن الكل متطابق) ويعمل barrier قبل ما الباقي يكمّلوا. في FSDP كل rank عنده شريحة بس، فإما تجمّعها قبل الحفظ أو كل rank يكتب shard بتاعه.
  • ما تخلطش بين الأنواع: الـ Data Parallel بيوزّع الداتا ويكرر الموديل. الـ FSDP بيوزّع الموديل (والـ optimizer والـ gradients بحسب الإعداد) كمان. وفيه أنواع تانية (tensor وpipeline parallel) الدرس مبيغطيهاش.
  • الـ communication cost: الـ all-reduce بيبعت حجم الـ gradients كله عبر الشبكة في كل step (الخوارزميات زي الـ ring بتخلي التكلفة لكل rank تقريبًا ثابتة مع زيادة عدد الـ ranks). عشان كده الـ accumulation مع no_sync بيخفض التكرار.
  • أخطاء شائعة: نسيان الـ broadcast فالـ ranks بتبدأ بقيم مختلفة، عدم تساوي عدد الـ collectives بين الـ ranks فالتدريب بيعلّق، استخدام نفس الـ batch على كل الـ ranks بدل شرايح مختلفة فبتضيّع الـ speedup، وحساب الـ loss المعروض على rank 0 بس وتفتكره متوسط الكل.
  • في الـ LLMs: موديلات اللغة الكبيرة (مليارات الـ parameters) بتتدرب بمزيج من الـ data parallel وsharding زي الـ FSDP، لأن الـ optimizer state والـ gradients بياخدوا ذاكرة أكتر من الـ weights نفسها (شوف المعمل في درس ٤٧٥).
